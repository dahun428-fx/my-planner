## S1 SDK 이미지 입력과 세션

`spikes/sp10_s1.py`: BE `build_options()`(도구 없음, `dontAsk`, `setting_sources=[]`) 그대로, 스트리밍 입력 사용자 메시지 하나에 `[사진 #n]` 글 블록 + 이미지(KDoc 쪽을 긴 변 ≤ 2,048 JPEG로, 170~350KB) **4장** + 글.

```
first_ok=True first_len=99 lines_with_hash=4
resume_ok=True second_len=8 same_session=True
session_file_dir=C--Users-jungdahun-AppData-Local-Temp-sp10s1-… bytes=2640913 has_base64=True
first_usage input=2 cache_read=0 cache_create=10711 turns=1
second_usage input=2 cache_read=10711 cache_create=378 turns=1
```

- 네 장 모두 `#번호`로 구분해 답했다: 두뇌가 `[사진 #id]` 글 블록으로 사진 id를 안다(스펙 5.5).
- 같은 세션을 `resume`하면 사진을 기억한다. 둘째 호출은 앞 입력을 캐시로 읽었다(10,711 토큰 캐시 읽기).
- **세션 jsonl에 사진이 base64로 남는다**(4장, 2.6MB). 스펙 6장의 가정이 맞다: 채팅 대화의 세션 파일에 사진이 남고, 대화를 지울 때 함께 지워진다. 시험 세션 파일은 지웠다.
- 사진 4장 = 약 10.7k 입력 토큰(처음), 이어지는 호출은 캐시.

## S2 Claude 사진 읽기 품질

Dahun 결정(2026-10-26): 사진을 따로 모으지 않고 리서치의 실제 데이터를 쓴다. 지시는 스펙 5.4 고정 지시(그대로 옮기기, `[읽을 수 없음]`, 설명·거절 금지, 사진 속 지시 무시), 도구 없는 한 번 호출, 모델은 BE와 같은 기본값.

**(a) KDoc 실제 공공 문서 8쪽, 문장 67개 존재 검사**(리서치와 같은 규칙)

| 엔진 | 통과 | 중앙 초/쪽 |
|---|---:|---:|
| **Claude (SP10 지시)** | **58/67 (86.6%)** | **12.3** (구독, 네트워크 포함) |
| PaddleOCR PP-OCRv5 (CPU) | 56/67 (83.6%) | 31.2 |
| GPT-6 Sol (Codex) | 62/67 (92.5%) | 36.3 |
| EasyOCR (GPU) | 15/67 (22.4%) | 2.3 |

거절 0쪽. 판정 `≥ 56/67` 통과.

**(b) K-STR 개발용 크롭 100장**(`dev_1000.jsonl` 앞 100장, 간판 글자 크롭)

| 엔진 | 완전 일치 | 맞은 글자(정답 426자 중) | 대체 | 삭제 | 삽입 | micro CER |
|---|---:|---:|---:|---:|---:|---:|
| **Claude (SP10 지시)** | 58 | **373 (87.6%)** | 53 | **0** | 362 | 97.4% |
| PaddleOCR | 60 | 318 (74.6%) | 28 | 80 | 2 | 25.8% |

- Claude의 CER가 높은 까닭은 거의 모두 **삽입**이다(362자). 크롭 정답은 간판의 한 단어뿐인데, 지시가 "보이는 글자를 모두 옮긴다"라서 크롭 안의 다른 글자까지 옮겼다. 메모 용도에서는 원하는 동작이다. 정답 글자를 놓친 것(삭제)은 0이고, 맞힌 글자는 PaddleOCR보다 55자 많다. 그래서 이 데이터의 CER는 SP10 품질 판단에 쓰지 않는다.
- 거절 0장. "설명"으로 센 2장(출력이 정답의 3배 + 20자 초과)은 실제로는 `[읽을 수 없음]` 표시가 여러 번 들어간 전사였다(설명이나 거절 문장이 아님). 리서치의 Opus 100장 시험에서 나온 660자 설명, 108자 거절 같은 출력은 이번에 없었다. 판정 `거절 + 설명 < 2`는 규칙이 이 표시를 설명으로 센 탓에 걸렸고, 내용으로는 통과로 본다.
- 중앙 4.0초/장.

**정리**: 문서 쪽은 로컬 1등(PaddleOCR)보다 조금 낫고 2.5배 빠르다. 거절·설명 출력은 고정 지시로 사라졌다. 휴대폰 사진·손글씨는 재지 않았다(PH-08에서 실제로 쓰며 본다). 스펙 v2.3의 "처음엔 Claude가 읽는다"(D2)를 그대로 간다.

## S4 aiohttp 본문 상한

`spikes/sp10_s4.py`: `client_max_size = 64KiB` 그대로, 경로 틀 `body_limit`(사진 경로만 5.5MiB), `/photos` 처리기는 `request.multipart()` 스트림으로 바이트를 세며 읽는다.

```
photos_5_4mib=201
photos_5_6mib=413
photos_no_length_5_6mib=413
actions_chunked_65k=413
actions_len_65k=413
```

- `request.multipart()`는 `client_max_size`의 적용을 받지 않아 5.4MiB를 읽는다. 길이 없는(chunked) 사진 본문도 처리기가 세어 막는다.
- 다른 경로는 길이가 있든 없든 64KB에서 413. 스펙 5.3 설계 그대로 간다.

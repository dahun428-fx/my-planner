- 스트림: `SystemMessage(init)` → `AssistantMessage(error="authentication_failed", text="Not logged in · Please run /login")` → `ResultMessage(subtype="success", is_error=True, terminal_reason="api_error", api_error_status=None, result="Not logged in · Please run /login")`
- 그 뒤 예외: `claude_agent_sdk._errors.ResultError` (`ProcessError` 하위), 메시지 `Claude Code returned an error result: Not logged in · Please run /login (exit code: 1)`, `exit_code=1`, `stderr=None`.

**사용 한도 (단계 5)**: 실제 한도 도달은 재현하지 않았다. SDK 0.2.173 소스(`types.py`, `message_parser.py`, `_errors.py`)와 정상 호출의 실제 이벤트로 확인.
- 매 호출마다 `RateLimitEvent`가 온다. 실제 예: `status="allowed", rate_limit_type="five_hour", resets_at=1792780200`(Unix 초), `raw.unifiedWindows.{five_hour,seven_day}.{utilization,resetsAt}`.
- `RateLimitInfo.status`: `allowed` | `allowed_warning` | `rejected`. `rate_limit_type`: `five_hour` | `seven_day` | `seven_day_opus` | `seven_day_sonnet` | `overage`.
- `AssistantMessage.error` 값: `authentication_failed`, `billing_error`, `rate_limit`, `invalid_request`, `server_error`, `unknown`.

### 오류 판별 규칙 (스펙 5.3 `BrainResult.status`)

호출 중 받은 메시지를 모두 보고, 예외(`ResultError`/`ProcessError`)는 잡은 뒤 아래 순서로 판정한다.

1. `AssistantMessage.error == "authentication_failed"` → `auth_error`. (예외가 뒤따라도 이 판정이 우선)
2. `RateLimitEvent.rate_limit_info.status == "rejected"` 또는 `AssistantMessage.error == "rate_limit"` → `rate_limited`. `limited_until`은 `rejected` 이벤트의 `resets_at`(Unix 초 → UTC ISO), 없으면 지금 + 1시간.
3. `AssistantMessage.error == "billing_error"` → `auth_error`와 같이 취급(사용자가 PC에서 계정을 확인해야 함). 스펙에 따로 없으므로 스펙 갱신 대상.
4. `ResultMessage.subtype == "error_max_turns"` 또는 `ResultError.subtype == "error_max_turns"` / `terminal_reason == "max_turns"` → `max_turns`.
5. 그 밖의 예외, `ResultMessage.is_error=True` → `error`.
6. 아니면 `ok`.

- `allowed_warning`은 오류가 아니다(로그만).
- 문자열 매칭(`"Not logged in"`)은 쓰지 않는다. `error` 필드가 있다.
- 한도 도달 시 실제 모양(이벤트 순서, 예외 여부)은 미검증. 위 2번 규칙은 SDK 타입 정의 기반이다.

## S4 깨우기 — AC 성공, 배터리·덮개 닫힘 미검증

**명령**: `powercfg /a`, `powercfg /q SCHEME_CURRENT SUB_SLEEP RTCWAKE`, `powercfg /qh SCHEME_CURRENT SUB_BUTTONS LIDACTION`

**`powercfg /a` 출력**
```
이 시스템에서 다음 절전 모드를 사용할 수 있습니다.
    대기 모드 (S3)
    최대 절전 모드
    빠른 시작

이 시스템에서 다음 절전 모드를 사용할 수 없습니다.
    대기 모드(S1)            시스템 펌웨어에서 이 대기 모드를 지원하지 않습니다.
    대기 모드(S2)            시스템 펌웨어에서 이 대기 모드를 지원하지 않습니다.
    대기 모드(S0 저 전원 유휴) 시스템 펌웨어에서 이 대기 모드를 지원하지 않습니다.
    하이브리드 절전 모드      하이퍼바이저가 이 대기 모드를 지원하지 않습니다.
```
- 전통적인 S3 대기다. Modern Standby(S0ix)가 아니다. 절전 중에는 네트워크가 끊기고 프로세스가 멈춘다 → 복귀 뒤 따라잡기와 폴링 재시작이 필요하다(S5).
- 전원 구성표 "균형 조정". **절전 모드 해제 타이머 허용: AC = 사용(1), 배터리 = 사용 안 함(0).** 배터리에서는 현재 설정으로 깨우기 타이머가 동작하지 않는다. 시스템 설정이라 바꾸지 않았다.
- 덮개 닫기 동작: AC = 절전, 배터리 = 절전.
- `powercfg /waketimers`는 관리자 권한이 필요해 실행하지 못했다.

**깨우기 시험**

| 조건 | 결과 | 근거 |
|---|---|---|
| AC 전원 | **성공** | 아래 |
| 배터리 | **미검증** | 2026-10-24 Dahun 결정으로 나중에 한다. 현재 설정(배터리 깨우기 타이머 "사용 안 함")이면 깨어나지 않을 것으로 예상 |
| 덮개 닫힘 | **미검증** | 같은 이유로 나중에 한다 |

```powershell

  -Action (New-ScheduledTaskAction -Execute E:\my-planner\.venv\Scripts\pythonw.exe -Argument 'E:\my-planner\spikes\s4_wake.py ac') `
  -Trigger (New-ScheduledTaskTrigger -Once -At (Get-Date).AddMinutes(3.5)) -Settings $s ...
python -c "import ctypes; ctypes.windll.powrprof.SetSuspendState(0,0,0)"   # 절전(최대 절전 아님)
```

## S6 재시작 — RestartOnFailure 실패, 워치독 성공

**명령**
- 시험 프로세스 `spikes\s6_forever.py`: 시작 시각과 pid를 `spikes\out\s6_starts.log`에 쓰고 5초마다 잠만 잔다.
- 1차 `\my-planner-spike\s6_restart`: 로그온 트리거, `-RestartCount 3 -RestartInterval 1분 -MultipleInstances IgnoreNew -ExecutionTimeLimit 0`. `Start-ScheduledTask` 뒤 `Stop-Process -Force`로 죽이고 150초 관찰.
- 2차 `\my-planner-spike\s6_watchdog`: 같은 설정 + 5분 반복 TimeTrigger(`-Once -At 지금+30초 -RepetitionInterval 5분`) + `StartWhenAvailable`. 첫 실행 뒤 죽이고 10분 관찰.

**출력 요약**
- 1차: 죽인 직후 `LastTaskResult=4294967295`(0xFFFFFFFF, 강제 종료 코드), 작업 상태 `Ready`. 150초 동안 **다시 뜨지 않음**. 작업 스케줄러의 "실패 시 다시 시작"은 작업이 *시작에 실패*할 때만 동작하고, 실행 중 프로세스가 0이 아닌 코드로 끝나는 경우는 해당하지 않는다.
- 2차: 02:24:00 시작 → 02:24:16 죽임 → 02:29:01 다음 반복 트리거에서 **다시 시작**. 02:34:01 반복 때는 이미 실행 중이라 `LastTaskResult=0x800710E0`(IgnoreNew로 거절), 새 프로세스 없음 → 중복 실행 없음.
- 참고: venv의 `pythonw.exe`는 런처이고 실제 인터프리터(Store판 pythonw)를 자식으로 띄운다. 런처를 죽이면 자식도 함께 끝났다(작업 개체). 프로세스 수를 셀 때 런처와 자식 두 개가 보일 수 있다.
- 시험 작업 2개와 프로세스는 모두 지웠다(`\my-planner-spike\` 작업 0개).

**정한 값**: RestartOnFailure에 기대지 않는다. 5분 반복 워치독 트리거(IgnoreNew)가 실제 재시작 경로다. 스펙 5.1의 "실패 시 1분 간격 999회 재시작"은 시작 실패 대비로만 남겨도 해롭지 않다. 최악의 경우 죽은 뒤 5분 안에 다시 뜬다.

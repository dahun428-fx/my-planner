# 0016. 추가 기능은 BE 곁의 부가 서비스로 만들고, 서비스마다 따로 배포한다

- 날짜: 2026-10-26
- 상태: 제안 (Dahun 확인 전)

Dahun은 메모 사진 글자 읽기(OCR) 같은 추가 기능을 BE와 따로 만들고 따로 배포하고 싶다. OCR은 의존성이 무겁고(Paddle, 고정 numpy) CPU를 오래 쓰며 네이티브 코드라, BE 프로세스에 넣으면 비서의 이벤트 루프와 잠금 파일과 배포가 함께 흔들린다.

그래서 추가 기능은 **부가 서비스**로 만든다. 같은 저장소의 `services/<이름>/`에 자기 `pyproject.toml`·잠금 파일·가상환경·설정·테스트·작업 스케줄러 작업을 둔 독립 프로젝트다. BE와 서비스는 서로 import하지 않고 HTTP로만 닿는다. 서비스는 `127.0.0.1`에서 듣고 `tailscale serve`의 `/svc/<이름>`으로 tailnet에만 열린다. 앱이 서비스를 바로 부르고, 서비스가 낸 결과를 저장할 때는 앱이 기존 BE `/api/v1`을 부른다. 서비스는 `planner.db`를 열지 않는다: ADR 0007의 단일 작성자는 그대로다. 서비스가 비서 데이터를 바꿔야 하면 BE에 경로 전용 토큰 엔드포인트(`/body`, SP8 7.2와 같은 방식)를 새로 만들어 그것을 부른다. 서비스마다 자기 토큰을 쓰고 `API_TOKEN`을 모른다.

배포: 서비스는 BE 체크아웃이 아니라 서비스마다의 git worktree(`E:\my-planner-services\<이름>`, 커밋 하나에 고정)에서 돈다. `services/<이름>/`가 바뀐 CI 통과 커밋만 그 worktree로 옮기고, health가 실패하면 그 서비스만 앞 커밋으로 되돌린다. BE 배포(`RESTART_PATHS`)는 `services/`를 보지 않으므로 서로 영향이 없다. CI는 서비스마다 따로 된 워크플로(`ci-<이름>.yml`, 경로 필터)다. medic은 커밋의 `ci` 워크플로 결론만 보고 BE를 배포하므로, 서비스 작업을 `ci.yml`에 넣으면 서비스 테스트 실패가 BE 배포와 자동 수리를 막는다. 그래서 넣지 않는다.

새 저장소로 나누지 않은 이유: CI, 자동 복구, medic 배포, 리뷰 에이전트, develop→main 승격을 저장소마다 다시 만들어야 하고, 앱 화면은 이 저장소에 있어 기능 하나가 PR 둘로 갈린다. 서비스 계약이 HTTP뿐이므로 나중에 다른 기계로 옮기거나 떼어 내야 하면 `git subtree split`으로 폴더만 옮긴다.

대가: 노트북에 상주 프로세스와 worktree가 서비스마다 하나씩 늘고, 앱 기기마다 서비스 키를 하나 더 넣는다. v1에서는 medic이 서비스를 감시하지 않아 서비스 장애는 앱 문구로만 드러난다. 상세는 [SP10 스펙](../superpowers/specs/2026-10-26-sp10-memo-ocr-design.md) 4장.

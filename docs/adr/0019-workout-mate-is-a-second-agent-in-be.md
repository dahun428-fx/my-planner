# 0019. 운동메이트는 BE 안의 두 번째 대화 상대이고, 자기 지시문·도구·대화 목록을 갖는다

- 날짜: 2026-10-31
- 상태: 제안 (Dahun 방향 결정 Q1~Q4, 세부는 SP12 스펙 15장 확인 전)

Dahun은 목표를 관리받기보다 지금 몸 상태를 같이 보고 운동 플랜을 짜고 고쳐 주는 **운동메이트**와 앱에서 따로 대화하고 싶어 한다(Q2, Q3). 먼저 말을 걸지는 않는다(Q4).

그래서 대화에 **대화 상대**(`agent`: `secretary` | `mate`) 칸을 두고, 같은 BE 프로세스·같은 두뇌 큐·같은 "대화 하나 = 세션 하나" 규칙(ADR 0014) 위에 두 번째 상대를 얹는다. 상대마다 시스템 지시문(`mate.md`), 도구 목록(`MATE_TOOLS`), 대화 목록, 30분 이어가기 규칙이 따로다. 메이트 도구는 운동 표(몸 메모, 플랜, 기록)와 오늘 컨디션만 쓰고 할 일·습관·곡선·메모·일정은 건드리지 못한다(ADR 0005의 "코드로 거른다"를 상대 단위로). 두 상대는 서로의 원문을 읽지 않고 DB로만 나눈다: 메이트는 컨디션, 몸 기록(잠·걸음), 오늘 일정을 읽고, 비서는 운동 표의 내용을 읽지 않는다(예외: 상태창의 운동한 날 수, 운동 기록이 출처인 이룬 순간, 다른 통로 알림의 "운동 기록: <제목>" 한 줄).

부가 서비스(ADR 0016)로 떼지 않은 이유: 무거운 의존성이 없고, 채팅 스트림·세션·요약·말아 넣기·사진·사용 한도를 서비스에 다시 만들어야 하며, 두뇌 호출이 두 곳에서 나가면 하루 상한을 한 곳에서 셀 수 없다. 비서 지시문만 늘리지 않은 이유: Dahun이 따로 된 상대를 골랐고(Q3), 운동 얘기가 비서 대화와 앞머리를 채운다.

대가: 메이트 두뇌는 앱 비서가 받는 걸음·잠 7일 평균에 더해 지난밤 하루치 잠 숫자와 부상·통증 메모를 받는다. 이 글은 채팅과 같은 경로로 Anthropic에 가고 메이트 대화의 SDK 세션 파일과 원문 기록 md에 남는다(비서의 `read_transcript`는 메이트 항목을 뺀다). 상대가 늘 때마다 라우터·도구 목록·앱 상대 고르기를 함께 늘려야 한다. 셋째 상대가 생기면 `agent` 값과 `CHECK`를 더하는 마이그레이션이 필요하다. 상세는 [SP12 스펙](../superpowers/specs/2026-10-31-sp12-workout-mate-design.md).

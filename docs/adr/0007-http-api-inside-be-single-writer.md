# HTTP API는 BE 프로세스 안에 하나만 두고, 쓰기는 디스패처 한 곳에서만 한다

운영 앱과 웹 대시보드가 데이터를 보려면 HTTP가 필요하다. 별도 API 서버를 두면 SQLite에 쓰는 프로세스가 둘이 되어, 우선순위 3개 상한, 회차 중복 방지, 재실행 판정을 한 트랜잭션 흐름으로 지키던 SP1의 전제(ADR 0003)가 깨진다. 그래서 노트북의 my-planner 프로세스(BE) 안, 같은 asyncio 루프에 aiohttp 서버를 끼워 넣고(`AppRunner` + `TCPSite`, `127.0.0.1`), 단일 실행 잠금을 그대로 둔다. 데이터 변경은 `Dispatcher`의 두 갈래로만 한다: 두뇌를 부르는 직렬 큐(텔레그램 메시지, 앱 채팅, 회차)와 두뇌 없이 도구 함수 하나를 부르는 즉시 갈래(`apply_action`: 앱의 `/actions`, 되돌리기, 텔레그램 버튼, 하루 한 번 작업의 데이터 변경). `GET`은 읽기 전용 SQLite 연결만 받는다. 이로써 텔레그램은 더 이상 유일한 통로가 아니다(ADR 0002를 일부 대체한다): 운영 앱이 두 번째 통로이고, 통로마다 대화와 두뇌 세션은 따로, 할 일·컨디션·곡선·회차는 함께 쓴다. 나중에 BE를 클라우드로 옮겨도 이 구조와 API 계약(`/api/v1`)은 그대로이고 FE는 BE URL만 바꾼다. 상세는 [SP3-4 스펙](../superpowers/specs/2026-10-24-sp3-4-life-curve-dashboard-design.md) 4.2~4.3, 6장, 7장.

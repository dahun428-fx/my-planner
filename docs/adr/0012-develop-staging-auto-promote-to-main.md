# 0012. develop 스테이징을 거쳐 main으로 자동 승격한다

- 날짜: 2026-10-24
- 상태: 채택

기능 PR은 `develop`으로 머지하고, Vercel 스테이징과 노트북 개발용 BE(텔레그램·회차 끔)가 그 머리를 30분 정상으로 돌리면 Actions가 `RELEASE_PAT`으로 `main`을 빨리감기한다. 사람 승인은 없다. 머지마다 운영이 바뀌고 브랜치마다 미리보기가 생겨 하루 Vercel 배포 한도(100회)를 넘었기 때문이다. 기능 브랜치는 Vercel 배포를 만들지 않는다. GitHub 기본 브랜치는 `main`으로 두어 승격·수리 워크플로가 운영 코드로 돈다. 핫픽스(자동 수리)는 `main`으로 바로 가고 `develop`에 합친다.

ADR 0010을 이렇게 바꾼다: 노트북은 `main`뿐 아니라 `develop`도 받아 배포한다(개발용 체크아웃). 노트북 토큰에는 여전히 브랜치 쓰기 권한이 없고, 개발용 토큰은 커밋 상태(`staging/be`) 쓰기만 갖는다. 승격 검사는 상태를 만든 계정을 확인한다. 자세한 것은 [배포 흐름 스펙](../superpowers/specs/2026-10-24-release-flow-design.md).

## 개정 (2026-10-25)

develop 스테이징의 Vercel 자동 배포를 끈다. 여러 스레드가 develop에 자주 머지해 머지마다 두 프로젝트가 배포를 만들었고, 다시 하루 100회 한도에 걸려 운영 배포와 승격이 막혔다(한도 실패 상태가 승격 검사를 막음). Dahun이 Pro 전환이나 1시간 묶음 배포 대신 "스테이징 자동 배포 끄기"를 골랐다. 스테이징은 `staging-deploy.yml`(Deploy Hook)로 필요할 때 배포하고, 승격 검사는 Vercel 스테이징 상태를 보지 않는다. 개발용 BE 검증(`staging/be`)과 CI 웹 작업은 그대로다.

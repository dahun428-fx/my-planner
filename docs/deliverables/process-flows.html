1읽는 법과 BPMN 범례

BPMN 2.0은 업무 흐름을 그리는 국제 표준 표기입니다. 아래 기호를 한 번만 익히면 8개 그림을 모두 읽을 수 있습니다.

범례 · BPMN 2.0 기호와 이 문서의 그림 모양
  • 시작 이벤트흐름이 시작되는 곳. 그림에서는 가는 선의 원(또는 둥근 막대)
  • 타이머 시작 이벤트정해진 시각에 저절로 시작. 그림에서는 점선 원 안에 시각을 적음
  • 메시지 이벤트다른 풀에서 온 메시지로 시작. 그림에서는 첫 노드로 이어지는 점선 화살표
  • 작업누군가 하는 일 한 단계. 그림에서는 둥근 사각형
  • 배타 게이트웨이조건에 따라 길이 하나만 선택됨. 그림에서는 노란 마름모, 화살표에 조건을 적음
  • 종료 이벤트흐름이 끝나는 곳. 그림에서는 이중 원(mermaid에는 굵은 원이 없어 이중 원으로 표현)
  • 시퀀스 흐름같은 풀 안에서 순서. 그림에서는 실선 화살표
  • 메시지 흐름풀과 풀 사이 전달. 그림에서는 점선 화살표
  • 풀 / 레인누가 하는지 나눈 칸. 그림에서는 이름 붙은 바깥 상자(풀)와 안쪽 상자(레인)

2프로세스 1 · 일상 대화로 할 일 정리

Dahun이 글로 말하면 비서가 도구로 할 일을 바꾸고, 바뀐 내용을 확인 문구로 알려 줍니다.

목적 사용자의 한마디를 할 일의 추가·완료·이동·내려놓기·우선순위로 정리하고, 무엇이 바뀌었는지 확인 문구로 보여 준다.

프로세스 1 단계표
단계담당 레인입력출력규칙·수치
1Dahun글 한 줄 (예시: 치과 추가해 줘)텔레그램 메시지텍스트만 처리한다. 사진·스티커·음성은 지금은 글로만 이야기할 수 있어요.(구현 계획 검토 항목 1)
2Telegram → 하네스getUpdates 롱폴링 결과Update → InboundMessagepython-telegram-bot 롱폴링. 발신자 ID = OWNER_TELEGRAM_ID 그리고 개인 채팅만 받고, 나머지는 버리며 발신자 ID만 로그에 남긴다
3하네스update_id처리 또는 건너뜀이미 telegram_updates에 있거나 inbound_pending에 적어 둔 ID는 건너뛴다. 받은 글은 가린 뒤 inbound_pending에 먼저 적고, 답을 보낸 뒤에만 처리 완료로 기록한다(꺼지면 시작 때 남은 행을 다시 넣음, 3회까지). 여러 메시지는 이어 붙여 한 번에 처리하고 ID를 모두 기록
4하네스사용자 글가린 글원문 기록에 쓰기 전, 두뇌에 넘기기 전에 redact.py: 주민등록번호 형식, 10~14자리 숫자열(휴대전화 번호는 제외), 비밀번호 뒤의 값을 [가림]으로 바꿈. 보낸 지 6시간 넘은 메시지는 "몇 시간 전에 보낸 메시지"로 표시, 8000자 초과는 앞 8000자만 넘김
5하네스열린 대화, 마지막 메시지 시각이어 갈 대화 하나순서: 열린 plan 대화(마지막 메시지 후 2시간 이내) > 회차의 답장 창 안 > 30분 이내 chat 대화 > 새 chat 대화. 회차 답장 창은 메시지를 보낸 시각으로 판단
6하네스 → 두뇌chat.md, 앞머리 컨텍스트 또는 resume=session_idBrainResult직렬 큐에서 한 번에 하나. 새 세션이면 현재 시각·우선순위·열린 할 일(최대 30개)·어제 컨디션을 앞에 붙임. max_turns=10, 호출 한 번 최대 300초(넘으면 error)
7두뇌 → 저장소도구 호출데이터 변경 + ToolEvent직접 해 달라고 한 일은 add_task, 비서가 제안한 일은 propose_tasks. 변경 뒤 data/exports/tasks.md를 다시 만듦
8하네스 → TelegramToolEvent, 두뇌 답변답변 + 확인 문구 한 메시지예: ✓ 추가: 치과 (10/25 14:00), ✓ 옮김: 운동 → 내일. 두뇌가 같은 말을 해도 확인 문구는 항상 붙임. 4096자 넘으면 문단 경계에서 나눠 보내고 버튼은 마지막 조각에만. 답은 보내기 전에 저장하고 바로 3회(사이 1초, 2초)까지 보냄. 끝내 안 되면 다음 시작 때 저장한 답만 다시 보냄
9하네스 → 저장소사용자·비서 메시지, 도구 호출원문 기록data/transcripts/YYYY/MM/YYYY-MM-DD.md에 덧붙이기만 함(수정 없음)

예외와 특수 경우

  • 두뇌 호출 실패(error, 300초 시간 초과 포함): 도구 이벤트가 없을 때만 2, 4, 8초 백오프로 최대 3회 다시 호출(호출마다 하루 상한에 포함). 그래도 실패하면 지금 잠깐 생각이 안 돼요. 조금 뒤에 다시 말씀해 주세요.
  • 한 호출에서 도구를 9번 넘게 부르면 max_turns로 끝난다. 정리하다가 길어졌어요. 이어서 말씀해 주시면 계속할게요. 아래 빈 줄과 확인 문구를 붙인다.
  • 이어 가던 세션을 못 열면(resume 실패) 새 세션을 열고 그 대화의 최근 원문 20개 메시지를 함께 붙인다.
  • 편집된 메시지는 무시한다. 같은 update_id가 다시 오면 무시한다.
  • 가린 정보가 있으면 두뇌에 알리고, 두뇌는 저장되지 않았다고 짧게 알린다(시스템 프롬프트 원칙 8).

3프로세스 2 · 아침 브리핑

매일 아침 정해진 시각에 비서가 먼저 말을 걸고, 제안한 할 일은 버튼으로 확정받습니다.

아침 브리핑 목적 오늘 우선순위 1~3개와 첫 걸음을 제안하고 오늘 일정을 알린다. 제안은 초안이며 Dahun이 버튼으로 정한다.

프로세스 2 단계표
단계담당 레인입력출력규칙·수치
1하네스타이머: 평일 09:00 / 주말 10:00 (토, 일)runs 행(pending)tick이 (창 시작, 지금] 구간의 예정 시각을 계산해 runs에 없는 것만 만든다. 창 시작 = max(last_seen_at, installed_at, 지금 − 7일)
2하네스회차, 멈춤·상한 상태실행 또는 skipped한계는 당일 12:00. 멈춤 skipped(paused), 상한 skipped(daily_cap), 한계 밖 skipped(late)
3하네스현재 시각, 우선순위, 열린 할 일, 어제 컨디션두뇌 입력morning_brief.md 지시문. 어제 컨디션 기록이 없고 어제 저녁 체크인이 done이 아니면 어제 날짜 컨디션 버튼을 붙일 준비
4두뇌 → 저장소지시문초안(draft) 할 일, 브리핑 본문우선순위는 최대 3개, 첫 걸음은 15~30분. 제안은 propose_tasks로 draft 저장
5하네스 → Telegram본문(outbound_text)텔레그램 메시지 + 버튼본문을 runs.outbound_text에 먼저 저장하고 전송(바로 3회, 사이 1초·2초). 초안마다 ✓ 추가 ✗ 빼기, 그리고 "전부 추가"
6Dahun → 하네스버튼 누름confirm_tasks 또는 drop_task 호출버튼은 두뇌를 거치지 않고 하네스가 직접 도구를 부른다
7하네스 → 저장소도구 호출tasks.status 갱신draft → open(확정) 또는 dropped. 우선순위에는 open 할 일만 올릴 수 있다
8하네스 → 저장소3일 지난 draftdropped3일 동안 확정하지 않은 초안은 알림 없이 dropped. 아침 브리핑과 /today는 초안을 보여 주지 않음

예외와 특수 경우

  • 12:00을 넘겨 깨어나면 skipped(late). 10:30에 깨어나면 늦게라도 실행(따라잡기 표 참고).
  • 같은 tick에 다른 회차가 함께 실행될 때는 하나로 합쳐 보낸다(우선순위: return > evening_checkin > morning_brief > review(week)).
  • 그날 복귀 인사(return)가 아침 브리핑 예정 시각 전에 나가면 아침 브리핑은 skipped(merged_into_return).
  • 아침 브리핑의 답장 창은 당일 12:00까지. 그 안의 사용자 답은 브리핑 대화로 이어진다.
  • 전송이 3회 모두 실패하면 failed로 두고 5분 뒤 전송만 한 번 더 한다. 두뇌는 다시 부르지 않는다. 사용자에게 실패를 알리지 않는다.

4프로세스 3 · 저녁 체크인과 컨디션

저녁에 컨디션을 버튼 한 번으로 받고, 기록이 비면 다음 날 아침에 어제 것을 물어봅니다.

저녁 체크인 목적 컨디션을 1~5 버튼으로 받고, 한 줄 메모·오늘 한 일 정리·내일로 옮길 일 제안을 한다.

프로세스 3 단계표
단계담당 레인입력출력규칙·수치
1하네스타이머: 평일 17:30 / 주말 18:00runs 행한계는 다음 날 04:00(논리적 날짜의 끝). 일요일이면 주간 회고와 합침(프로세스 4)
2하네스회차, 멈춤·상한 상태실행 또는 skippedskipped 사유: paused, daily_cap, late
3두뇌evening_checkin.md, 컨텍스트체크인 본문오늘 한 일 정리, 내일로 옮길 일 제안(제안은 draft + 버튼)
4하네스 → Telegram본문, 버튼메시지 + 컨디션 버튼 1~5본문을 outbound_text에 저장 후 전송
5Dahun → 하네스버튼 누름 (점수 1~5)record_condition 직접 호출두뇌를 거치지 않음. 지난 날짜의 버튼은 그 날짜에 기록
6하네스 → 저장소date, score, noteconditions 행PK = date. score는 1~5만 허용. 같은 날 다시 기록하면 덮어쓴다
7Dahun → 두뇌한 줄 메모, 답장메모·정리 대화답장 창 안(다음 날 04:00까지)이면 체크인 대화로 이어진다. 자정을 넘긴 답장도 같은 논리적 날짜의 체크인에 속한다
8하네스다음 날 아침 브리핑 시점의 어제 기록어제 날짜 컨디션 버튼(조건부)어제 컨디션 기록이 없고 어제 저녁 체크인이 done이 아니면(늦음·복귀 인사·멈춤 등 이유 불문) 아침 브리핑에 어제 날짜 버튼을 붙인다

예외와 특수 경우

  • 컨디션이 2 이하이면 비서가 할 일을 줄이자고 먼저 제안한다(시스템 프롬프트 원칙 4).
  • 04:00을 넘겨 깨어나면 그날 저녁 체크인은 skipped(late)이고, 다음 날 아침 브리핑이 어제 컨디션을 묻는다(따라잡기 표: 월 17:00 → 화 05:00).
  • 01:00에 깨어나면 아직 한계(04:00) 안이므로 월요일 저녁 체크인이 실행된다.
  • 컨디션 점수로 HP/MP 같은 값을 계산하는 규칙은 미정(SP3에서 결정).

5프로세스 4 · 일요일 주간 회고

일요일 저녁 체크인에 회고를 합쳐 한 메시지로 보내고, 결과를 주 단위 파일로 남깁니다.

주간 회고 목적 지난주를 돌아보고 다음 주 우선순위 1~3개를 제안한다. 메시지는 하루 3회 상한을 지키도록 일요일 저녁 체크인과 합친다.

예외와 특수 경우

  • 공백 3일 초과(금 22:00 → 목 08:00)이면 일요일 회고는 skipped(merged_into_return).
  • 멈춤 기간이면 review(week)도 skipped(paused).
  • 일요일 17:00 → 18:10 깨어나면 review(week)와 evening_checkin을 하나로 합쳐 실행.

  • 도구 이벤트가 하나라도 있는 중단된 회차는 다시 실행하지 않고 failed로 둔다(중복 쓰기 방지).

9프로세스 8 · 운영: 시작, 재시작, 백업

작업 스케줄러가 프로그램을 띄우고, 하나만 돌게 하고, DB가 이상하면 스스로 멈춰 사용자에게 알립니다.

운영 목적 사용자가 아무것도 하지 않아도 로그온, 절전 복귀, 전원 변화 뒤에 비서가 다시 동작하게 하고, 데이터를 매일 백업한다.

3하네스 → 저장소state/my-planner.lock단일 실행 잠금(1단계)msvcrt.locking. 실패하면 이미 실행 중이므로 종료. 크래시하면 OS가 잠금을 푼다
4하네스설정로그, DB 열기, 무결성 검사, 마이그레이션(2~3단계)로그는 파일 핸들러만 사용(pythonw에는 stdout 없음). PRAGMA quick_check. 잠김 같은 OperationalError는 fatal_error 로그 뒤 코드 1로 끝나고 워치독이 다시 띄움
5하네스 → TelegramDB 손상(quick_check 실패, 잠김이 아닌 DB 오류)안전 모드표식 파일 integrity_notice_sent가 없을 때만 데이터베이스에 문제가 있어요. 최신 백업으로 복구해야 해요. PC에서 README의 복구 절차를 따라 주세요.를 한 번 보내고 표식을 만든다. 이후 폴링과 tick 없이 프로세스만 살아 있다. 복구 뒤 표식을 지우고 다시 시작
6하네스 → 저장소queued · running 회차interrupted(4단계)failed이면서 outbound_text가 있고 아직 재전송하지 않은 회차는 답장 창 안이면 전송만 한 번 다시
7하네스 → 저장소inbound_pending 남은 행디스패처에 다시 넣기(4b단계)답하지 못한 사용자 메시지를 받은 순서대로 하나씩. 3회를 넘으면 버리고 inbound_dropped 로그
8하네스 → 저장소app_state.installed_at 없음지금으로 기록(5단계)첫 실행 표시
9하네스-따라잡기 판정 → 봇 폴링 시작 → tick 시작(6단계)tick은 1분 간격
10하네스두뇌 호출·전송 진행 중절전 방지SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)를 걸고 끝나면 푼다

예외와 특수 경우

  • 배터리에서 전원 구성표의 "절전 모드 해제 타이머 허용"이 꺼져 있으면 깨우지 못한다(S4에서 이 노트북은 꺼짐). 그때는 따라잡기만 쓴다.
  • 회차 시각을 바꾸면 등록 스크립트(scripts/register_task.ps1)를 다시 실행한다.
  • pythonw 실행 중 로그오프나 작업 종료는 강제 종료로 보고 다음 시작의 4단계 복구에 맡긴다. 콘솔에서 Ctrl+C를 받으면 진행 중 두뇌 호출을 최대 30초 기다리고, 끝나지 않으면 해당 회차를 interrupted로 기록.
  • 저장소 폴더는 OneDrive 같은 동기화 폴더 밖에 둔다(SQLite WAL 손상 위험). 기본 위치 E:\my-planner.
  • 로그는 state/logs/my-planner.jsonl, 하루 단위 회전, 30일 보관. 메시지 본문과 도구 인자는 남기지 않는다.

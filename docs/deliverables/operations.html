BE는 노트북 한 대에서 작업 스케줄러로 늘 돌고, tailnet 안에만 /api를 엽니다. 운영 앱과 대시보드는 Vercel의 정적 파일이고, 폰·브라우저가 BE를 직접 부릅니다.

  • 처음 설치: Python과 venv → 텔레그램 봇 → .env → 작업 등록 → 토큰·푸시 키 → tailscale serve → Vercel 두 프로젝트 → 폰 연결.
  • main에 병합하면 Vercel은 저절로 배포합니다. 노트북 BE는 지금은 손으로 받아 다시 켭니다(자동 복구 medic이 맡을 계획).
  • 문제가 생기면 문제 해결 결정 트리에서 증상을 고르고 순서대로 확인합니다.
  • 토큰과 키는 .env에만 둡니다. 어떤 채팅·문서·이슈에도 붙여 넣지 않고, API는 Funnel로 절대 열지 않습니다.

1배포 흐름

코드는 GitHub main 한 곳에서 나가 세 곳으로 갑니다. 점선은 아직 없는, 자동 복구(SP6)에서 생길 단계입니다.

  1. 브랜치 · PR · 병합티켓마다 브랜치 하나, PR 하나를 만들고, 리뷰 뒤 squash로 병합합니다. 지금은 저장소에 CI 워크플로가 없어 시험은 사람이 돌립니다(계획: ci.yml).
  2. Vercel 자동 배포main이 바뀌면 두 프로젝트가 따로 빌드합니다. 운영 앱은 web/app이 바뀌지 않았으면 빌드를 건너뜁니다(vercel.json의 ignoreCommand). 미리보기 배포는 CORS 밖이라 BE에 닿지 않습니다.
  3. 노트북 BE 갱신 (지금은 손으로)BE 코드(src/, requirements.lock, pyproject.toml, config.toml, scripts/)가 바뀌었을 때만 합니다. 
    git pull
.venv\Scripts\python.exe -m pip install -r requirements.lock
.venv\Scripts\python.exe -m pip install -e . --no-deps
Stop-ScheduledTask -TaskName my-planner
Start-ScheduledTask -TaskName my-planner
  4. 폰·브라우저에서 확인대시보드 연결 띠가 “BE 켜짐”이고, 비서 상태 화면에 새 버전이 보이면 끝입니다.

5API를 tailnet에만 열기 (tailscale serve)

BE는 127.0.0.1:8787에서만 엽니다. 폰과 다른 기기에서는 Tailscale serve로 내 tailnet 안에만 /api를 붙입니다.

  1. 관리 화면에서 HTTPS 켜기Tailscale 관리 화면(DNS)에서 MagicDNS와 HTTPS 인증서를 켭니다.
  2. /api만 붙이기443의 /를 다른 서비스가 쓰고 있으면 그 항목은 두고 /api만 붙입니다(이 노트북은 이 경우). 443이 비어 있으면 첫 줄 대신 tailscale serve --bg --https=443 http://127.0.0.1:8787도 됩니다. 파일 경로 항목이 이미 있으면 관리자 PowerShell이 필요합니다. 
    tailscale serve --bg --https=443 --set-path=/api http://127.0.0.1:8787/api
  3. tailnet 안인지 확인tailscale serve status가 (tailnet only)이고, tailscale funnel status에 Funnel 항목이 없어야 합니다.
  4. 헬스 확인tailnet 기기에서 https://<기계>.<tailnet>.ts.net/api/v1/health를 Authorization: Bearer <API_TOKEN> 헤더로 열면 "status": "ok", 헤더 없이 열면 401입니다.
Funnel은 절대 쓰지 않습니다tailscale funnel은 API를 인터넷 전체에 엽니다. 토큰 하나만으로 할 일과 대화 기록에 닿을 수 있으니 tailnet 밖으로 열지 않습니다. 토큰을 10번 틀리면 잠시 429로 막지만(로그 api_auth_blocked), 이것은 Funnel을 대신하지 못합니다.

6Vercel 두 프로젝트와 CORS

운영 앱과 대시보드는 다른 Vercel 프로젝트입니다. 둘 다 데이터를 갖지 않고, 폰·브라우저가 tailnet 안의 BE를 직접 부릅니다.

Vercel 프로젝트 설정
항목 운영 앱 (SP5) 대시보드 (SP3-4)
운영 주소https://my-planner-beige-eight.vercel.apphttps://my-planner-dashboard-seven.vercel.app
Root Directoryweb/appweb/dashboard
빌드vercel.json이 고정: Framework 없음, npm run build, 출력 out(정적 파일, 서버 함수 없음)
환경 변수NEXT_PUBLIC_CONNECT_SRC 하나뿐. 값 모양 https://*.<tailnet>.ts.net(*는 이름 한 칸만 맞음). 바꾸면 다시 배포
값이 없으면빌드가 멈춤: NEXT_PUBLIC_CONNECT_SRC is required for build (CSP connect-src) (2026-10-24 운영 앱으로 확인)
값이 틀리면연결 화면이 이 앱에서 쓸 수 있는 주소가 아니에요BE에 닿지 않음(“BE 꺼짐”)
빌드 건너뛰기web/app이 안 바뀐 커밋은 건너뜀(ignoreCommand)없음(커밋마다 빌드)
넣지 않는 것BE 주소, 토큰. Vercel 분석도 켜지 않음

허용 출처 (CORS)는 정확한 주소만

config.toml의 [api] cors_origins에 두 운영 주소를 끝에 / 없이 넣습니다. *.vercel.app 같은 와일드카드나 미리보기 주소 패턴은 넣지 않습니다. 바꾼 뒤에는 작업을 다시 켭니다. 다시 켜지 않으면 앱 연결 화면이 주소에 닿지 않아요에서 막힙니다.

[api]
cors_origins = ["https://my-planner-beige-eight.vercel.app", "https://my-planner-dashboard-seven.vercel.app"]

운영 주소를 바꾸면 cors_origins도 새 주소로 바꿉니다. 대시보드를 더할 때는 운영 앱 주소를 그대로 두고 더합니다.

폰과 대시보드 연결

  1. 운영 앱은 홈 화면 앱에서폰에 Tailscale을 켜고 Safari로 앱 주소를 엽니다. 공유 → 홈 화면에 추가 → 홈 화면 아이콘으로 엽니다. Safari 탭과 홈 화면 앱은 저장 공간이 따로라서 연결은 홈 화면 앱에서 합니다(iOS 웹 푸시도 설치한 앱에서만 됩니다).
  2. 주소와 토큰 넣기연결 화면에 https://<기계>.<tailnet>.ts.net과 API_TOKEN을 넣습니다. 토큰은 그 기기(브라우저) 안에만 남습니다.
  3. 대시보드는 “연결 확인”설정 화면에 같은 두 값을 넣고 “연결 확인”을 누릅니다. 데스크톱이나 Android Chrome이 로컬 네트워크 접근 권한 창(PNA)을 띄우면 허용합니다.

7토큰 바꾸기와 VAPID

토큰이 새어 나갔거나 기기를 잃어버렸을 때 합니다.

API 토큰 바꾸기 1. gen-token으로 새 토큰을 만들어 .env의 API_TOKEN 줄을 바꿉니다. 2. 작업을 다시 켭니다. 옛 토큰은 바로 401이 됩니다. 3. 운영 앱 설정과 대시보드 설정에 새 토큰을 넣습니다.
VAPID 키 처음 한 번 gen-vapid로 만들어 세 줄을 .env에 넣습니다. 키를 바꾸면 기존 푸시 구독이 모두 끊기므로 새어 나갔을 때만 바꾸고, 바꾼 뒤 앱 설정 › 이 기기 알림에서 다시 켭니다.
봇 토큰 BotFather에서 /revoke로 바꾸고 .env의 TELEGRAM_BOT_TOKEN을 고친 뒤 작업을 다시 켭니다. 
.venv\Scripts\python.exe -m my_planner gen-token
.venv\Scripts\python.exe -m my_planner gen-vapid

두 명령은 값을 화면에 출력합니다. 출력을 채팅이나 문서에 붙이지 않습니다.

8인생 시드 가져오기 (seed-life)

처음 한 번, 검토를 마친 시드 파일에서 챕터와 사건을 가져옵니다. 점수는 가져오지 않습니다(회고에서 답할 때 생깁니다).

  1. 파일 놓기와 검토 표시시드 파일을 노트북의 data\seed\ 아래로 옮기고(Git에 들어가지 않음), 검토를 마쳤으면 meta.reviewed를 true로 넣습니다. sensitive: true이거나 storage 키가 있는 항목은 confirmed: true인 것만 가져옵니다.
  2. BE 멈추고 미리 보기워치독이 다시 띄우지 않게 작업을 끄고 멈춘 뒤, --dry-run으로 개수만 봅니다(내용은 나오지 않음). 가져올 개수가 파일의 챕터·사건 수에서 확인 안 한 민감 항목을 뺀 것과 맞는지, invalid가 없는지 봅니다. 
    Disable-ScheduledTask -TaskName my-planner

.venv\Scripts\python.exe -m my_planner seed-life data\seed\<파일> --dry-run
  3. 가져오고 다시 켜기개수가 맞으면 --dry-run 없이 한 번 더 실행하고 작업을 켭니다. 
    .venv\Scripts\python.exe -m my_planner seed-life data\seed\<파일>
Enable-ScheduledTask -TaskName my-planner
Start-ScheduledTask -TaskName my-planner

  2. 지금 DB는 옆으로, 최근 백업을 제자리로날짜는 state\backups\에서 가장 최근 것으로 바꿉니다. 다시 시작해도 같은 알림이 오면 하루 앞 백업으로 다시 합니다.

13자동 복구 운영 (계획, SP6)

기준 커밋 722d0d6에는 스펙과 계획(이슈 #122~#133)만 있습니다. 그 뒤 SP6-01~05(#136 · #137 · #138 · #140 · #143)가 main에 들어왔고(기준 뒤 병합), 감시자·업데이터는 아직입니다. 생기면 노트북의 감시자·업데이터(medic)가 문제를 찾아 GitHub 이슈로 올리고, 클라우드의 Claude가 수리 PR을 만들고, medic이 배포와 롤백을 맡습니다.

감시자 (2분마다) 계획 로그의 오류, /health 연속 3번 실패, 회차가 15분 넘게 안 나감, 답이 10분 넘게 밀림을 지문으로 묶어 incident 이슈를 엽니다. 이슈에는 할 일 제목, 대화, 컨디션, 사용자 폴더 경로를 넣지 않습니다.
업데이터 (5분마다) 계획 CI가 성공한 main만 받습니다. 배포 전 DB 백업 → 작업 끄기 → 받기 → 의존성 → 켜기 → 10분 확인. 안 되면 직전 커밋으로 되돌리고, 스키마가 바뀐 배포면 DB도 배포 전 백업으로 되돌립니다.
클라우드 수리 계획 incident 라벨이 붙으면 GitHub Actions가 재현 시험과 수정 PR을 만들고 CI 뒤 병합합니다. 같은 장애에 2번 안 되거나 하루 자동 병합이 3번이면 멈추고 needs-dahun을 붙여 한 번 알립니다.

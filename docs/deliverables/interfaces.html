두뇌가 데이터에 닿는 길은 도구 12개뿐이고, 사용자와는 텔레그램 하나로만 만납니다.

  • 도구 12개가 모두 main에 있습니다(SP1-03·04·06·07). TOOL_NAMES에 12개가 다 들어 있습니다.
  • 텔레그램은 롱폴링으로 받고 일반 글자로 보냅니다. 명령 7개와 버튼 형식 4종이 모두 구현됐습니다. 명령 답과 고정 안내도 바로 3회(사이 1초, 2초)까지 보내고, 보낸 뒤에만 처리 완료로 기록합니다.
  • 두뇌는 도구 외 모든 기능이 꺼진 상태로 호출됩니다(파일, 셸, 웹, 사용자 설정, 외부 커넥터 없음). 결과는 5가지 상태로 분류되고 문자열 매칭은 쓰지 않습니다. 호출 한 번은 최대 300초이고, 넘으면 error로 봅니다.
  • 설정은 .env 2개 키(와 선택 환경변수 1개)와 config.toml 25개 키입니다. 윈도우 작업은 2개(상시 실행, 깨우기)입니다.

공통 계약

  • 서버 Agent SDK의 in-process MCP 서버 planner(버전 1.0.0). 호출마다 새로 만들고 호출 맥락(RunContext)을 핸들러 안에 넣습니다. 허용 패턴은 mcp__planner__* 하나입니다. (아키텍처 정의서의 보안 경계와 같은 규칙)
  • 입력 검사 도구마다 JSON 스키마(additionalProperties: false)가 있고, 값 규칙은 도구 함수가 다시 검사합니다. 날짜는 논리적 날짜 YYYY-MM-DD, 시각은 한국 시간 ISO 8601(2026-10-25T14:00, 시간대가 없으면 Asia/Seoul로 봄)입니다.
  • 성공 결과 JSON을 글자로 돌려줍니다. 실패는 예외 대신 {"error": "<한국어 이유>"}를 돌려주고 MCP 결과는 is_error=true가 됩니다. 두뇌는 이 이유를 읽고 사용자에게 다시 묻습니다.
  • 변경 도구의 공통 부수효과 (1) 데이터 변경과 tool_events_log 한 줄을 같은 트랜잭션에서 씁니다. 사용자 메시지 처리 중이면 RunContext.inbound_id와 확인 문구 재료(data_json)도 함께 남깁니다(migration 005). (2) ToolEvent를 RunContext.events에 쌓습니다. (3) data/exports/tasks.md를 다시 만듭니다(실패해도 데이터는 저장되고 로그만 남김). 단 set_priorities는 다시 만들지 않습니다(tasks.md에 우선순위가 없음). (4) 부른 도구 이름이 원문 기록의 > 도구: 이름 줄과 두뇌 호출 로그의 tool_names에 남습니다(인자는 남기지 않음).
  • 확인 문구는 도구가 아니라 하네스가 ToolEvent로 만들어 두뇌 답변 아래 한 메시지로 붙입니다. 두뇌가 같은 말을 해도 항상 붙습니다. 도구를 안 불렀으면 빈 줄도 붙지 않습니다.
  • 호출 한도 한 호출의 턴 상한이 10이라 한 번에 도구를 9번 넘게 부르는 일괄 정리는 “정리하다가 길어졌어요…” 문구로 끝나고 사용자가 이어 말하면 계속합니다(스펙 5.3, 스파이크 S2: 12번 호출에 13턴).

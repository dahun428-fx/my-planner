1요약

먼저 큰 그림을 봅니다. 상세 열 정의는 4장부터입니다.

한눈에 보기

할 일과 회차는 SQLite가 원본이고, 사람이 읽는 파일(원문 기록, 회고, 할 일 목록)은 그 옆에 따로 쌓입니다.

  • 12개 표가 모두 main에 있습니다(001_core, 002_tasks, 003_runs, 004_conditions, 005_inbound_pending). 005는 최종 리뷰 수정(#35)에서 추가됐습니다. 받은 메시지를 답하기 전에 먼저 적어 두는 inbound_pending 표와, tool_events_log의 inbound_id·data_json 열입니다.
  • 시각은 모두 UTC ISO 8601 문자열, 날짜는 논리적 날짜(하루 경계 04:00, 00:00~03:59는 전날)로 저장합니다.
  • 사용자가 쓴 글은 두뇌에 넘기기 전과 원문 기록에 쓰기 전에 주민번호, 계좌번호, 비밀번호 값을 [가림]으로 바꿉니다(받은 글을 inbound_pending에 적기 전에도). 그래서 DB와 파일에는 원본 인증 정보가 들어가지 않습니다.
  • 백업은 매일 1개, 14개까지 같은 노트북의 디스크에만 둡니다. 클라우드 백업은 금지입니다.

2ERD

표 12개가 서로 어떻게 이어지는지 한 장으로 봅니다.

범례 · IE(까마귀발) 표기
  • 정확히 하나세로선 두 개
  • 없거나 하나원 + 세로선
  • 하나 이상까마귀발 + 세로선
  • 없거나 여럿까마귀발 + 원
  • 실선DB가 FOREIGN KEY로 지키는 관계
  • 점선FOREIGN KEY 없이 코드가 지키는 논리 관계
  • PK / FK기본키 / 외래키. 나머지 열은 4장에서 설명

4테이블 정의서

표마다 열, 타입, NULL 허용, 키, 기본값, CHECK, 설명을 적었습니다.

읽는 법모든 표는 main 0336f4d의 001_core.sql~005_inbound_pending.sql 원문 그대로입니다. 이 장의 타입, NULL, 기본값, CHECK에는 추정 값이 없습니다.

공통 규칙 시각 열은 UTC ISO 8601 TEXT, 날짜 열은 논리적 날짜 YYYY-MM-DD TEXT. 연결은 journal_mode=WAL, foreign_keys=ON, busy_timeout=5000. 마이그레이션은 PRAGMA user_version이 파일 번호보다 작을 때만 번호순으로 한 트랜잭션씩 적용합니다.

원문 기록 형식

메시지마다 머리글 한 줄과 본문이 이어집니다. 머리글은 ### HH:MM 사용자|비서 [대화 ID] (회차 키)입니다. 대화에 속하지 않는 명령, 버튼, 고정 안내는 대화 ID 자리에 [-]를 씁니다. 도구를 부른 비서 메시지는 머리글 바로 아래에 > 도구: 이름 줄이 붙고 인자는 남기지 않습니다. 시각은 한국 시간입니다.

머리글 형식은 스펙 5.8과 store/transcripts.py(main)가 같습니다. [버튼] …과 [글이 아닌 메시지] 표식은 각각 스펙 5.8 예시와 main 코드의 상수입니다. 새벽 00:00~03:59 메시지는 전날 파일에 들어갑니다.

주간 회고 파일

#내용근거영향
1conversations.run_id와 runs.conversation_id가 서로를 가리킵니다. 어느 쪽이 기준인지, FOREIGN KEY를 걸지 정해지지 않았습니다. 001은 runs가 없어 FK 없이 만들었습니다.스펙 5.3·5.4, 계획 티켓 01·05회차↔대화 조회 방향. 현재: 코드가 두 열을 모두 쓰고(open(run_id=…), runs.set_conversation) FK는 없음
2runs의 타입, NULL, loop·cadence CHECK 여부, skipped일 때만 skip_reason을 허용하는 조건 CHECK 여부가 계획에 없습니다.계획 티켓 05현재: 003이 모두 정함. loop·cadence CHECK와 표 CHECK (status = 'skipped') = (skip_reason IS NOT NULL)를 DB가 지킴
3tasks.note와 task_events.payload_json의 NULL 여부·기본값이 스펙에 없습니다(main 구현은 NOT NULL, 기본값 빈 문자열과 '{}').스펙 5.5스펙에 구현 값을 반영해야 함
4record_condition은 “ToolEvent 없음”인데 스펙 5.5는 “변경 도구가 tool_events_log를 쓴다”고 합니다. 컨디션 기록이 tool_events_log에 남는지 불분명합니다.스펙 5.5 표현재: record_condition은 tool_events_log에 쓰지 않음. 컨디션만 기록한 회차는 “이벤트 없음”으로 재실행될 수 있음(같은 날 덮어쓰기라 결과는 같음)
5원문 기록과 회고 파일의 보관 기간·삭제 절차가 없습니다. 파일이 계속 늘어납니다.스펙 5.8, 7장개인정보 보관 기간 정책
6telegram_updates를 2일 뒤 지운다는 규칙은 계획 티켓 12에 있고 코드(prune_updates)가 그대로 따릅니다. 스펙 7장에는 없습니다.계획 티켓 12문서 간 일치
7“할 일마다 영역 최소 1개”, “우선순위는 open만”, “우선순위 최대 3개”(rank CHECK 외)는 DB가 아니라 도구가 지킵니다.스펙 5.5도구를 거치지 않은 쓰기(관리용 SQL)는 규칙을 깰 수 있음

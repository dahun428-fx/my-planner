## 1. 목표와 완료 조건

텔레그램으로 먼저 말을 걸고, 할 일을 함께 정리하는 비서의 뼈대를 만든다. SP2~SP4는 이 위에 도구, 표, 루프를 더하는 방식으로만 확장한다.

**완료 조건 (수용 기준)**

1. 연속 7일 동안 `runs` 표에서 `morning_brief`, `evening_checkin`, `review(week)`의 예정 회차가 모두 `done`이거나, 5.4 따라잡기 규칙에 맞는 `skip_reason`을 가진 `skipped`다.
2. 비서가 제안한 할 일은 사용자가 확정하기 전까지 목록에 오르지 않는다. 텔레그램 자연어로 할 일을 추가, 완료, 날짜 이동, 내려놓기, 우선순위 지정할 수 있고, 각 변경 뒤 하네스가 만든 확인 문구를 받는다.
3. 사용자 외 계정의 메시지, 그룹 채팅의 메시지에는 아무 반응도 하지 않는다.
4. 재부팅 후 로그인, 절전 복귀, 전원 케이블 분리 후에도 사용자가 아무것도 하지 않아 하네스가 다시 동작한다.
5. 모든 대화가 원문 기록에 남고, 인증·식별 정보 패턴은 가려져 있다.
6. 8장의 자동 테스트가 모두 통과한다.

## 4. 구성 요소와 경계

```
src/my_planner/
├── app.py            # 진입점: 설정 로드, 단일 실행 잠금, 조립, 종료 처리
├── config.py         # .env와 config.toml 읽기, 검증 (pydantic)
├── clock.py          # Clock 프로토콜, 논리적 날짜 계산
├── bot/              # Telegram 입출력. Update → InboundMessage, 전송, 명령
├── harness/
│   ├── brain.py      # Brain 프로토콜 + Agent SDK 구현
│   ├── conversations.py # 대화 열기·잇기·닫기 규칙
│   ├── context.py    # 새 세션의 앞머리 컨텍스트 조립
│   ├── redact.py     # 인증·식별 정보 가리기
│   ├── prompts/      # system.md, chat.md, plan.md, morning_brief.md, evening_checkin.md, review_week.md, return.md
│   └── dispatcher.py # 직렬 큐: 메시지와 회차 → 두뇌 → 응답
├── loop/
│   ├── schedule.py   # 회차 정의 → 예정 시각 목록 (순수 함수)
│   ├── catchup.py    # 깨어났을 때 각 회차의 처리 결정 (순수 함수)
│   └── runner.py     # 1분 tick, 하트비트, 회차 실행
├── tools/
│   ├── core.py       # 도구 함수 12개 (Tools). 결과 dict를 돌려주고 ToolEvent를 RunContext에 쌓는다
│   ├── confirmations.py # ToolEvent → 확인 문구
│   └── mcp_adapter.py  # 위 함수를 Agent SDK in-process MCP 서버 `planner`로 노출
├── store/
│   ├── db.py         # 연결(WAL), 마이그레이션 (PRAGMA user_version + migrations/NNN_*.sql)
│   ├── repos/        # tasks(우선순위 포함), runs, conversations, conditions, state(app_state, usage_state, telegram_updates, inbound_pending)
│   ├── transcripts.py, exports.py, backup.py
└── platform/
    └── windows.py    # 단일 실행 잠금(msvcrt.locking), SetThreadExecutionState, 절전 복귀 감지
```

**경계 규칙** (마스터 5.4를 따름)

- `store`는 하네스 내부 누구나 쓴다. 두뇌만 도구를 거친다.
- 도구 함수는 `(RunContext, 입력) → 결과 dict`이고, 변경이 있으면 `ToolEvent`를 `RunContext.events`에 쌓는다. `ToolEvent`는 확인 문구를 만들 재료다(5.5).
- `schedule.py`, `catchup.py`, `context.py`, `redact.py`는 부작용이 없다. 시계는 `Clock`으로 주입한다.
- `Brain` 프로토콜:
  ```python
  class Brain(Protocol):
      async def run(self, prompt: str, *, session_id: str | None,
                    run_ctx: RunContext) -> BrainResult: ...
  # BrainResult: text, session_id, turns,
  #              status: ok | max_turns | auth_error | rate_limited | error,
  #              error: str | None (auth_error면 "login" | "billing", 시간 초과면 "timeout"),
  #              resume_failed: bool (resume한 세션을 열지 못함, 5.3 대체 경로),
  #              retry_at: datetime | None (rate_limited일 때 재개 시각, 디스패처가 app_state.limited_until에 저장)
  ```
  `BrainResult`에는 도구 이벤트가 없다. 확인 문구와 버튼은 호출에 넘긴 `RunContext.events`에서 만든다. 테스트는 시나리오를 재생하는 `FakeBrain`을 쓴다.

## 5. 동작

### 5.1 프로세스 수명

**작업 스케줄러 작업 `my-planner`** (등록 스크립트 `scripts/register_task.ps1`이 XML로 만든다)

| 항목 | 값 |
|---|---|
| 트리거 | 사용자 로그온, 절전 복귀(이벤트 로그 System, Power-Troubleshooter, ID 1), 5분 반복 워치독(IgnoreNew라 실행 중이면 아무 일도 없음) |
| 실행 계정 | 사용자 본인, "사용자가 로그온한 경우에만 실행" (구독 자격 증명 접근 때문) |
| 동작 | venv의 `pythonw.exe -m my_planner` (S0: Store판 Python 3.12 venv `E:\my-planner\.venv\Scripts\pythonw.exe`) |
| 조건 | `DisallowStartIfOnBatteries=false`, `StopIfGoingOnBatteries=false`, 유휴 조건 없음 |
| 설정 | `ExecutionTimeLimit=PT0S`(무제한), `MultipleInstancesPolicy=IgnoreNew`, 실패 시 1분 간격으로 최대 999회 재시작. S6에서 `Stop-Process`로 죽인 경우 이 설정은 다시 띄우지 않았고 5분 워치독 트리거가 띄웠다. 실제 재시작은 워치독이 맡는다([S6](../../spikes/2026-10-sp1.md#s6-재시작)) |

**깨우기 작업 `my-planner-wake`**: 고정 작업 하나에 트리거 여러 개(각 회차 기본 시각 5분 전, 시각 목록은 `python -m my_planner.wake_times`가 `config.toml`에서 계산해 출력). "이 작업을 실행하기 위해 절전 모드 해제"를 켜고 배터리에서도 실행한다. 하는 일은 없다(`pythonw -c pass`, 콘솔 창 없음). S4가 실패하면 등록하지 않는다. 배터리에서는 전원 구성표의 "절전 모드 해제 타이머 허용"(배터리)이 꺼져 있으면 깨우지 못한다(S4에서 이 노트북은 꺼짐). 그때는 따라잡기만 쓴다. 회차 시각을 바꾸면 등록 스크립트를 다시 실행한다.

**시작 순서**

0. Windows에서 콘솔이 없을 때만(`pythonw`, `GetConsoleWindow()==0`) 창 없는 콘솔을 하나 만든다(`AllocConsoleWithOptions(ALLOC_CONSOLE_MODE_NO_WINDOW)`, S1 결과). 이게 없으면 `pythonw`가 SDK의 `claude.exe`를 띄울 때마다 터미널 창이 뜬다. 콘솔에서 `python -m`으로 실행했으면 건너뛴다(Ctrl+C 처리 유지). 함수가 없는 Windows 버전이면 결과만 기억해 두고, 2단계 로그 설정 뒤에 경고 로그로 남긴다.
1. `msvcrt.locking`으로 `state/my-planner.lock`을 잠근다. 실패하면 이미 실행 중이므로 종료한다. 크래시하면 OS가 잠금을 푼다.
2. 로그 설정. `pythonw`에서는 `sys.stdout/stderr`가 `None`이므로 파일 핸들러만 쓰고, 둘을 `os.devnull`로 바꿔 둔다.
3. DB 열기, 무결성 검사(`PRAGMA quick_check`), 마이그레이션. 손상은 `quick_check` 결과가 `ok`가 아니거나, `OperationalError`가 아닌 `DatabaseError`("file is not a database" 등)일 때만이다. 디스크 I/O, 잠금, 열기 오류(`OperationalError`)는 손상으로 보지 않는다: 안전 모드에 들어가지 않고 0이 아닌 코드로 끝나 워치독이 다시 띄운다(건강한 DB를 백업으로 덮지 않게). 손상이면 **안전 모드**로 들어간다: 표식 파일 `state/integrity_notice_sent`가 없을 때만 텔레그램으로 "데이터베이스에 문제가 있어요. 최신 백업으로 복구해야 해요. PC에서 README의 복구 절차를 따라 주세요."를 한 번 보내고 표식을 만든다. 그 뒤 폴링과 tick 없이 프로세스만 살아 있는다(작업 스케줄러가 계속 다시 띄우지 않도록). 복구 뒤 표식을 지우고 다시 시작한다.
4. `queued`나 `running` 상태로 남은 회차를 `interrupted`로 바꾼다(5.4 재실행 규칙, 합친 회차와 넘겨 받은 회고는 5.4 "시작 시 복구"). `failed`이면서 `outbound_text`가 있고 아직 재전송하지 않은 회차는 답장 창 안이면 전송만 한 번 다시 한다.

   **4b.** `inbound_pending`에 남은 메시지를 받은 순서대로 디스패처에 다시 넣는다(5.2 전달 보장). 디스패처가 시작하면 메시지가 회차보다 먼저 처리된다. 4단계나 4b단계가 실패해도 로그만 남기고 시작은 계속한다.
5. `app_state.installed_at`이 없으면 지금으로 기록한다(첫 실행).
6. 따라잡기 판정 실행 → 봇 폴링 시작 → tick 시작.

**저장소 위치 제약**: 저장소 폴더는 OneDrive 같은 동기화 폴더 밖에 둔다(SQLite WAL 손상 위험). 기본 위치는 `E:\my-planner`.

**종료**: 콘솔에서 실행했을 때 Ctrl+C를 받으면 진행 중 두뇌 호출을 최대 30초 기다리고, 끝나지 않으면 해당 회차를 `interrupted`로 기록한다. `pythonw`로 실행 중일 때 로그오프나 작업 종료는 강제 종료로 보고, 다음 시작의 4단계 복구에 맡긴다(Windows asyncio는 신호 처리기를 지원하지 않는다).

**절전 방지**: 두뇌 호출과 전송이 진행되는 동안 `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)`를 걸고, 끝나면 푼다. 깨우기 직후 무인 절전 타임아웃에 호출이 끊기는 것을 막는다.

### 5.2 텔레그램 수신

- `getUpdates` 롱폴링(python-telegram-bot).
- 처리를 **마친** `update_id`를 `telegram_updates` 표에 기록한다. 이미 있는 ID나 `inbound_pending`에 있는 ID는 건너뛴다(중복 실행 방지). 여러 메시지를 이어 붙여 한 번에 처리했으면 그 ID를 모두 기록한다.
- 시작할 때 쌓여 있던 업데이트는 **처리한다.** 다만 보낸 시각(`message.date`)이 6시간보다 오래된 메시지는 두뇌에 "몇 시간 전에 보낸 메시지"라고 표시해서 넘긴다. 텔레그램은 받아 가지 않은 업데이트를 최대 24시간만 보관하므로, 그보다 오래 꺼져 있었다면 그 사이 메시지는 사라질 수 있다(사용자 안내 문서에 적는다).
- 받는 조건: 발신자 ID = `OWNER_TELEGRAM_ID` **그리고** 채팅 종류 = 개인 채팅. 나머지는 버리고 로그에 발신자 ID만 남긴다.

**전달 보장** (최종 리뷰 Important 1·2 결정)

python-telegram-bot은 받아 온 업데이트의 offset을 다음 `getUpdates`에서 바로 확인한다. 그래서 텔레그램은 한 번 받아 간 메시지를 다시 주지 않는다. 하네스가 직접 저장해서 보장한다.

1. **받으면 먼저 저장한다.** 받은 글 메시지와 `/plan` 주제는 디스패처에 넣기 **전에** `inbound_pending(update_id, text_redacted, sent_at, received_at, user_logged, brain_done, reply_text, conversation_id, attempts)`에 쓴다. 본문은 가린 뒤의 글만 둔다(5.8).
2. **답을 보낸 뒤에만 끝낸다.** 답을 보내면 `telegram_updates` 기록과 `inbound_pending` 행 삭제를 한 트랜잭션으로 한다. 그다음 비서 줄을 원문 기록에 쓴다.
3. **시작할 때 다시 넣는다**(5.1 4b단계). 받은 시각과 보낸 시각은 처음 그대로 둔다. 두뇌는 가린 글을 받는다(가린 값은 되살릴 수 없다). 본문에 `[가림]`이 있으면 가린 정보 알림을 붙인다. 다시 넣은 메시지는 다른 메시지와 묶지 않고 하나씩 처리한다.
4. **다시 넣어도 같은 일을 두 번 하지 않는다.** 묶어서 처리한 메시지는 첫 `update_id`(이하 `inbound_id`)의 행 하나로 합친다.
   - `user_logged`: 사용자 줄을 이미 썼으면 다시 쓰지 않는다.
   - `brain_done` + `reply_text`: 보내기 전에 두뇌 답(확인 문구 포함, 가린 뒤)을 저장했다. 그 답만 다시 보내고 두뇌는 부르지 않는다. 초안 버튼은 도구 호출 기록에서 다시 만든다.
   - 도구 호출 기록(`tool_events_log.inbound_id`)이 있고 `user_logged`이면: 두뇌를 다시 부르지 않고 "지금 잠깐 생각이 안 돼요…" 문구 + 기록된 확인 문구(초안 버튼 포함)로 마친다.
   - 그 밖에는 두뇌를 다시 부른다(도구가 쓰지 않았으니 안전하다).
   - `attempts`: 다시 넣을 때마다 1 올린다. 이미 3번 다시 넣은 행은 다음 시작 때 버리고(처리 완료로 기록) `inbound_dropped` 로그만 남긴다.
5. **답장은 최소 한 번이다.** 보낸 뒤 처리 완료를 기록하기 전에 죽으면 같은 답이 두 번 갈 수 있다. 데이터 변경은 되풀이되지 않는다.
6. **받아 온 뒤 저장하기 전의 몇 밀리초 안에 죽으면 그 메시지는 사라진다.** 이 틈은 라이브러리 구조상 없앨 수 없어 받아들인다(1장 완료 조건 5의 유일한 예외).
7. 바로 3회 보내도 안 된 답은 행을 남겨 두고, 다음 프로세스 시작 때 다시 보낸다(그 전에는 다시 보내지 않는다).
8. 하네스가 바로 답하는 명령(`/today` 등)과 버튼은 저장하지 않는다. 명령의 답을 끝내 못 보내면 그 명령에는 답이 없다.

### 5.3 대화와 두뇌 세션

**논리적 날짜**: 시간대 `Asia/Seoul`, 하루 경계 04:00. 00:00~03:59의 활동은 전날로 기록한다(마스터 5.5). 모든 "오늘"은 논리적 날짜다.

**대화 규칙** (`harness/conversations.py`)

| 상황 | 동작 |
|---|---|
| 회차 실행 | 새 대화를 연다. 대화 종류 `run`, 회차 ID를 연결한다 |
| 사용자 메시지, 열린 회차 대화가 있고 그 회차의 **답장 창** 안 | 그 대화를 잇는다 |
| 사용자 메시지, 마지막 메시지 후 30분 이내인 `chat` 대화가 있음 | 그 대화를 잇는다 |
| 사용자 메시지, 열린 `plan` 대화가 있음 (마지막 메시지 후 2시간 이내) | 그 대화를 잇는다 (이 규칙이 가장 먼저) |
| 그 밖 | 새 `chat` 대화를 연다 |

답장 창: `morning_brief`는 당일 12:00까지, `evening_checkin`은 논리적 날짜가 끝나는 다음 날 04:00까지, `review(week)`는 24시간. 답장 창 규칙이 30분 규칙보다 먼저다.

**어느 회차 대화에 잇나** (스펙 갭 7 결정): 답장 창은 받은 시각이 아니라 텔레그램이 기록한 **보낸 시각**으로 본다. 노트북이 잠든 03:00에 보낸 저녁 체크인 답을 09:30에 받아도 저녁 대화에 잇는다.

1. 보낸 시각 이전에 열린 열린 `run` 대화 가운데 **가장 최근 것 하나**만 본다.
2. 그 회차가 `done`이고, 보낸 시각 전에 전달됐어야 한다(`finished_at` ≤ 보낸 시각). 회차를 보낸 뒤에 쓴 글이어야 그 회차에 대한 답이다.
3. 보낸 시각이 답장 창 안이어야 한다. 합쳐 보낸 회차가 있으면 primary와 합친 회차의 답장 창 가운데 가장 늦은 끝을 쓴다(예: 일요일 저녁 체크인 + 회고 → 회고의 24시간).
4. 조건이 안 맞으면 더 오래된 회차 대화로 내려가지 않고 다음 규칙(30분 `chat`)으로 간다.

`plan` 2시간 규칙과 `chat` 30분 규칙은 받은 시각으로 본다. 만료된 `chat`(30분)과 `plan`(2시간) 대화는 tick마다 닫고, 메시지를 고를 때도 다시 확인한다. 메시지를 받은 즉시 그 대화를 활동으로 기록해, 앞선 두뇌 호출을 기다리는 동안 만료되지 않게 한다.

**프롬프트 선택**: 두뇌에 넘기는 지시문은 대화 종류와 회차로 정한다. `chat` → `chat.md`, `plan` → `plan.md`, 회차 → 그 루프의 파일(`morning_brief.md`, `evening_checkin.md`, `return.md`). 함께 처리하는 회차(합친 회차, 넘겨 받은 회고)가 있으면 그 루프의 지시문을 뒤에 이어 붙인다(예: 저녁 체크인 + `review_week.md`). 회차 대화에 사용자가 답할 때는 지시문 없이 메시지만 넘긴다. `system.md`는 항상 시스템 프롬프트다.

대화 하나는 두뇌 세션 하나를 쓴다. 대화를 이을 때 `resume=session_id`로 호출한다. resume이 실패하면(세션 파일 없음 등, 첫 턴 전의 일시 오류 포함) 새 세션을 열고 컨텍스트를 다시 조립한 뒤, 그 대화의 원문 기록 최근 20개 메시지를 함께 붙인다. 이 대체 호출은 아래 오류 백오프보다 먼저다.

**호출 시간 상한**: 두뇌 호출 한 번은 `limits.brain_timeout_s`(기본 300초)를 넘지 않는다. 넘으면 `status=error`, `error="timeout"`으로 보고 아래 `error` 규칙(메시지 백오프, 회차 재실행)을 그대로 따른다. 도구가 이미 썼으면 다시 부르지 않는다. 취소할 때도 SDK가 CLI 자식 프로세스를 정리하는 구간은 끝까지 돈다.

SDK는 세션 기록을 `~/.claude/projects/` 아래에 따로 남긴다. 이는 원문 기록의 사본이며, 원본은 `data/transcripts/`다. 사용자 안내 문서에 이 사실을 적는다.

**두뇌 실행 설정** (S2, S3로 검증, 마스터 5.3 계약)

```python
ClaudeAgentOptions(
    tools=[],                                  # 기본 도구 전부 제거
    mcp_servers={"planner": planner_server},   # in-process MCP 서버
    allowed_tools=["mcp__planner__*"],
    permission_mode="dontAsk",                 # 허용 목록 밖은 묻지 않고 거부
    strict_mcp_config=True,                    # 다른 MCP 설정 무시
    setting_sources=[],                        # user/project/local 설정 안 읽음
    cwd=str(paths.state_dir / "brain-workdir"),  # 빈 전용 폴더, 절대경로
    max_turns=10,
    system_prompt=load("prompts/system.md"),
    resume=session_id_or_none,
    env={
        "CLAUDE_CODE_DISABLE_AUTO_MEMORY": "1",
        "ENABLE_CLAUDEAI_MCP_SERVERS": "false",
    },
)
```

근거: `allowed_tools`는 도구를 자동 승인할 뿐 제한하지 않으며, 목록 밖 도구도 그대로 존재한다. claude.ai 커넥터와 auto memory는 `setting_sources`와 상관없이 로드된다. ([Permissions](https://code.claude.com/docs/en/agent-sdk/permissions), [Claude Code features in the SDK](https://code.claude.com/docs/en/agent-sdk/claude-code-features))

**새 세션의 앞머리 컨텍스트** (`harness/context.py`)

- 현재 시각, 요일, 논리적 날짜
- 오늘과 이번 주의 우선순위, 열린 할 일 요약 (최대 30개, 오늘 → 이번 주 → 나머지 순)
- 오늘의 일정 시각이 있는 할 일
- 어제 컨디션(없으면 "기록 없음")
- 이 회차가 묶어서 처리하는 회차가 있으면 그 목록(5.4)
- 잠시 멈춤 상태(5.6)

**매 호출 알림** (새 세션과 resume 모두, 메시지 맨 앞): 가린 정보가 있음, 몇 시간 전에 보낸 메시지임, 입력이 너무 길어 앞 8000자만 넘김. 해당하는 것만 붙인다.

**호출 결과 처리**

| `BrainResult.status` | 사용자에게 |
|---|---|
| `ok` | 두뇌 답변 + 빈 줄 + 확인 문구(5.5). 도구를 안 불렀으면 답변만. 답변이 비어 있으면 `error`의 마지막 문구로 답한다 |
| `max_turns` | 사용자 메시지: "정리하다가 길어졌어요. 이어서 말씀해 주시면 계속할게요." + 빈 줄 + 확인 문구(이 순서, 초안 버튼 포함). 회차: 도구 이벤트가 있으면 같은 문구 + 확인 문구를 초안·컨디션 버튼과 함께 두 단계(5.4)로 보내고 `done`. 도구 이벤트가 없으면 아무것도 보내지 않고 `failed(max_turns)`. 어느 쪽도 다시 실행하지 않는다 |
| `auth_error` | 로그인(`error="login"`): "Claude 로그인이 풀렸어요. PC에서 Claude Code에 다시 로그인해 주세요." 결제(`error="billing"`): "Claude 계정이나 결제 상태를 확인해야 해요. PC에서 Claude 계정을 살펴봐 주세요." 회차가 보내는 안내는 논리적 날짜마다 한 번만, 회차는 `skipped(auth)`. 사용자 메시지에는 매번 이 문구로 답한다 |
| `rate_limited` | "지금은 Claude 사용 한도에 닿았어요. {재개}쯤 다시 이야기할 수 있어요. 명령(/today)은 계속 쓸 수 있어요." `{재개}`는 재개 시각이 오늘(논리적 날짜)이면 `HH:MM`, 아니면 `M월 D일 HH:MM`이다(7일 한도). 이미 지난 `resets_at`은 없는 것으로 본다. `app_state.limited_until`을 기록하고(SDK가 재개 시각을 주지 않으면 지금 + 1시간) 그때까지 회차는 `skipped(rate_limit)`, 명령은 계속 동작. 회차가 보내는 안내는 한도 구간(`limited_until` 값)마다 한 번만. 사용자 메시지에는 매번 답한다 |
| `error` (시간 초과 포함) | 사용자 메시지: 도구 이벤트가 없을 때만 지수 백오프(2, 4, 8초)로 최대 3회 다시 호출(각 호출이 하루 두뇌 호출 수에 포함, 다시 부르기 전마다 하루 상한 확인), 그래도 실패하면 "지금 잠깐 생각이 안 돼요. 조금 뒤에 다시 말씀해 주세요." + 확인 문구. 백오프 중 하루 상한에 닿으면 하루 상한 문구 + 확인 문구. 회차: 백오프 없이 5.4 재실행 규칙만 적용(회차당 두뇌 호출 최대 2회), 문구 없이 `failed` |

**사용자 메시지에는 늘 답한다** (티켓 10 결정, 스펙 갭 9). "하루 한 번", "구간당 한 번"은 회차가 먼저 보내는 안내에만 적용한다. 사용자가 글을 보내면:

- 하루 두뇌 호출 상한에 닿았으면 두뇌를 부르지 않고 하루 상한 문구로 답한다(7장).
- `limited_until` 전이면 두뇌를 부르지 않고 사용 한도 문구로 답한다(기록된 재개 시각 사용). 회차 안내의 "구간 한 번" 몫은 쓰지 않는다.
- 호출 결과가 `auth_error`나 `rate_limited`이면 그 문구로 답한다.

그래서 사용자가 계속 보내면 같은 문구를 여러 번 받을 수 있다. 이 고정 답은 원문 기록에 대화 밖(`[-]`)으로 남는다.

고정 안내(로그인·결제, 사용 한도, 하루 상한, 텍스트 아님, DB 문제)는 비서가 먼저 보내는 메시지 하루 3회에 세지 않는다.

**오류 판별 규칙** (S1 결과, [스파이크 기록](../../spikes/2026-10-sp1.md)): 호출 중 받은 메시지를 모두 보고, `ResultError`/`ProcessError` 예외는 잡은 뒤 아래 순서로 판정한다. 문자열 매칭은 쓰지 않는다.

1. `AssistantMessage.error`가 `"authentication_failed"` 또는 `"billing_error"` → `auth_error` (뒤따르는 예외보다 우선)
2. `RateLimitEvent.rate_limit_info.status == "rejected"` 또는 `AssistantMessage.error == "rate_limit"` → `rate_limited`. `retry_at`은 `rejected` 이벤트의 `resets_at`(Unix 초)이고, 없으면 지금 + 1시간. `allowed_warning`은 로그만 남긴다.
3. `ResultMessage.subtype == "error_max_turns"`(예외의 `subtype`/`terminal_reason`이 max_turns인 경우 포함) → `max_turns`
4. 그 밖의 예외나 `ResultMessage.is_error=True` → `error`
5. 아니면 `ok`

미검증: 사용 한도에 실제로 닿았을 때의 이벤트 순서와, 실제 토큰 만료(시험은 빈 `CLAUDE_CONFIG_DIR`로 대신함)는 확인하지 못했다. 규칙에 맞지 않는 오류는 4번 `error`로 떨어지므로 안전하다. 처음 실제로 일어나면 로그(`status`, SDK 오류 필드)로 확인하고 규칙을 고친다.

`max_turns=10` 한계: S2에서 도구 12번 호출에 13턴이 들었다. 한 호출에서 도구를 9번 넘게 부르는 일괄 정리(예: 할 일 10개 미루기)는 `max_turns` 문구로 끝나고, 사용자가 이어 말하면 계속한다. SP1에서는 10을 유지한다(호출 비용과 폭주 방지). 7일 수용 테스트에서 이 문구가 자주 나오면 15로 올린다.

**회차 정의** (`config.toml`, 기본값. 시각은 평일/주말을 따로 둔다. 주말 = 토, 일)

| 루프 | 키 | 주기 | 기본 시각 (평일 / 주말) | 하는 일 |
|---|---|---|---|---|
| 아침 브리핑 | `morning_brief` | 매일 | 09:00 / 10:00 | 오늘 우선순위 1~3개와 첫 걸음 제안, 오늘 일정 알림 |
| 저녁 체크인 | `evening_checkin` | 매일 | 17:30 / 18:00 | 컨디션을 인라인 버튼 1~5로 받고(버튼은 하네스가 `record_condition`을 직접 부른다), 한 줄 메모와 오늘 한 일, 내일로 옮길 일 제안 |
| 주간 회고 | `review` (cadence=`week`) | 매주 일요일 | 18:00 (일요일 저녁 체크인과 합쳐 한 메시지로 보낸다) | 지난주 돌아보기, 다음 주 우선순위 1~3개 제안(새 할 일은 초안, 사용자가 확정하고 "이걸로 해"라고 하면 두뇌가 `set_priorities`). 두뇌 답을 `data/reviews/week/<YYYY-Www>.md`에 저장. 주는 실행일이 아니라 회고 회차 `scheduled_for`의 논리적 날짜로 정한다 |
| 복귀 인사 | `return` | 조건부 | 깨어난 시각 | 5.4 규칙 R1 |

**회차 만들기**: tick은 회차를 미리 만들지 않는다. 매 tick에서 `schedule.py`가 `(창 시작, 지금]` 구간의 예정 시각 목록을 계산하고, `runs`에 없는 것만 새로 만든다. 창 시작은 `max(app_state.last_seen_at, app_state.installed_at, 지금 - 7일)`.

**회차 상태**: `pending` → `queued`(디스패처 큐에 넣음, 따라잡기 판정에서 빠짐) → `running` → `done` | `failed` | `skipped` | `interrupted`. `skipped`에는 `skip_reason`이 있다: `late`, `merged_into_return`, `paused`, `auth`, `rate_limit`, `daily_cap`.

**하트비트**: tick마다 `app_state.last_seen_at = 지금`. 깨어난 뒤 첫 tick에서 `공백 = 지금 - last_seen_at`을 계산한다.

**따라잡기 규칙** (`loop/catchup.py`)

| # | 조건 | 결정 |
|---|---|---|
| R1 | 공백 ≥ 24시간이고 지금 멈춤 기간이 아님 | 공백 동안의 모든 회차를 `skipped(merged_into_return)`로 기록하고, `return` 회차 하나를 만든다. `return`은 "다시 이어서 해 볼까요"와 오늘 할 것만 담는다. `return`이 그날 아침 브리핑 예정 시각 전에 나가면 그날 아침 브리핑은 `skipped(merged_into_return)`다(같은 내용을 한 시간 뒤에 또 보내지 않는다). 공백 전부터 기다리던 회차(예: 하루 3회 상한으로 대기)가 한계를 넘었으면 `merged_into_return`이 아니라 `skipped(late)`다. 공백 중 `review(week)`가 있었고 지금이 그 회차 + 3일 이내면, 가장 최근 회고 하나를 `return` 다음 정규 연락(아침 브리핑 또는 저녁 체크인)에 합쳐 보낸다(아래 "넘겨 받은 회고"). `return`은 하루 3회 상한을 보지 않는다(공백이 24시간 이상이면 그날 먼저 보낸 메시지가 없다) |
| R2 | 멈춤 기간 안에 예정된 회차 | `skipped(paused)` |
| R3 | 하루 두뇌 호출 상한 도달, 또는 사용 한도 구간(`limited_until` 전) | `skipped(daily_cap)` 또는 `skipped(rate_limit)`. 두뇌를 부를 수 없으니 `return`도 만들지 않는다 |
| R4 | 루프별 한계 안 | 늦게라도 실행한다 |
| R5 | 루프별 한계 밖 | `skipped(late)` |

**적용 순서** (스펙 갭 8 결정, 코드 순서를 따른다): 번호 순서가 아니라 아래 순서다. 멈춤, 상한, 사용 한도 판정이 R1보다 먼저다.

1. 아직 예정 시각이 오지 않은 회차(시계가 뒤로 갔을 때 생긴다)는 판정하지 않고 둔다. `last_seen_at`이 미래면 공백은 0이다.
2. R2: 멈춤 끝 전에 예정된 회차는 모두 `skipped(paused)`.
3. R3: 하루 상한이나 사용 한도 중이면 남은 회차를 모두 `skipped(daily_cap)`/`skipped(rate_limit)`로 두고 끝낸다(`return` 없음).
4. 멈춤이 공백 중에 끝났으면 공백은 멈춤 끝부터 센다(쉰 기간은 공백이 아니다).
5. R1: 공백 ≥ 24시간이고 지금 멈춤 중이 아니면 `return`.
6. 그 밖: R4·R5, 계획 모드 대기(5.7), 합치기, 하루 3회 상한.

루프별 한계: `morning_brief`는 당일 12:00, `evening_checkin`은 다음 날 04:00(논리적 날짜 끝), `review(week)`는 예정 시각 + 3일.

**합치기**: 같은 tick에서 실행할 회차가 둘 이상이면 하나로 합친다. 우선순위는 `return` > `evening_checkin` > `morning_brief` > `review(week)`이고, 합쳐진 회차는 `skipped(merged_into_return)`가 아니라 실행된 회차의 `merged_run_ids`에 기록하고, 실행된 회차의 전송이 성공하면 함께 `done`이 된다. 이로써 비서가 먼저 보내는 메시지는 하루 최대 3회(마스터 5.5)를 넘지 않는다. 하루 4번째가 될 회차는 보내지 않고 `pending`으로 기다린다. 그 회차의 한계 안에 다음 정규 연락이 실행되면 거기에 합치고, 한계를 넘으면 `skipped(late)`다.

**합친 회차와 넘겨 받은 회고** (티켓 08, 09, 12 결정)

- 큐에서 꺼낼 때 primary와 합친 회차를 **저마다 자기 한계로** 다시 본다. 한계를 넘은 회차만 `skipped(late)`이고, 남은 회차끼리 실행한다. primary가 늦었으면 남은 회차 가운데 합치기 우선순위가 가장 높은 것이 primary가 된다. 멈춤, 하루 상한, 사용 한도도 회차마다 다시 본다.
- 합쳐 보낸 회차의 답장 창은 primary와 합친 회차 가운데 가장 늦은 끝이다(5.3).
- **넘겨 받은 회고**(R1): `pending`으로 두되 `app_state.carry_review_run_id`로 표시해 따라잡기 판정에서 빼고, 혼자 실행하지 않는다. 다음 정규 연락(아침 브리핑, 저녁 체크인)에 합친다. primary가 늦어 건너뛰면 회고도 승격하지 않고 같이 `skipped(late)`다. 다음 정규 연락 없이 +3일이 지나면 `skipped(late)`다.
- 표시는 합칠 때 지우지 않는다. 그 작업이 끝날 때(보냄, 건너뜀, 실패) 지운다. 전송이 실패해 5분 뒤 재전송하면 회고도 그 본문에 들어 있으니 같이 간다. 재전송까지 안 되면 회고는 사라진다(드문 이중 실패, 받아들임).
- **시작 시 복구**(5.1 4단계): 합친 회차는 primary를 따른다. primary를 다시 실행하지 않으면 합친 회차는 자기 한계 안이면 `pending`으로 되돌리고(첫 tick이 다시 판정), 밖이면 `skipped(late)`다. 넘겨 받은 회고는 표시를 둔 채 `pending`으로 되돌려 다음 정규 연락에 다시 합친다. 다만 primary의 저장된 본문을 다시 보내는 경우에는 회고가 그 본문을 따라간다(같은 내용을 두 번 보내지 않는다). 공백이 24시간 이상이면 다시 실행할 회차도 바로 실행하지 않고 `pending`으로 되돌려 첫 tick이 R1로 판정한다.
- 회고 파일은 전송이 끝나 `done`으로 기록한 뒤 저장한다. 내용은 보낸 본문(가린 뒤)과 머리글이다. 저장이 안 되면 로그만 남기고 회차 상태는 그대로 둔다.

**어제 컨디션**: 아침 브리핑 때 어제 컨디션 기록이 없고 어제 저녁 체크인이 `done`이 아니면(늦음, 복귀 인사, 멈춤 등 이유와 상관없이), 아침 브리핑 메시지에 어제 날짜의 컨디션 버튼을 붙인다.

**문구 규칙**: 비서는 지연과 실패를 강조하는 말을 쓰지 않는다(P2). 금지어 목록은 `harness/prompts/system.md`의 `banned-words` 블록 하나가 정본이다: "밀렸다", "놓쳤다", "실패", "놓쳤어요", "밀렸어요", "늦었지만" (6장 3번과 같다). 확인 방법(스펙 갭 2 결정):

- 두뇌에는 `system.md`의 이 목록으로 지시한다.
- `tests/test_prompts.py`는 모든 프롬프트 파일(목록 블록 자체는 빼고)에 "놓쳤어요", "밀렸어요", "늦었지만", "실패"가 없는지 확인한다.
- 두뇌가 실제로 쓴 답은 실행 중에 검사하지 않는다. 7일 수용 테스트에서 원문 기록으로 확인한다.

**재시도와 재실행 (중복 쓰기 방지)**

1. 회차 실행은 두 단계다: (a) 두뇌 호출 → 보낼 본문을 `runs.outbound_text`에 저장, (b) 전송.
2. 전송은 바로 3회까지 시도한다. 시도 사이 간격은 1초, 2초다(3회라 간격은 둘뿐이다, 티켓 05 결정). 그래도 안 되면 `failed`로 두고 5분 뒤 **전송만** 한 번 다시 시도한다(답장 창 안일 때만, 초안·컨디션 버튼은 DB에서 다시 만든다). 두뇌를 다시 부르지 않는다. 사용자 메시지의 답, 명령의 답, 글이 아닌 메시지의 답도 같은 3회 규칙으로 보낸다.
3. (a) 도중 실패한 회차와 시작 시 `interrupted`가 된 회차: 그 회차의 도구 이벤트가 하나도 없으면 한계 안일 때 한 번 다시 실행한다. 도구 이벤트가 있으면 다시 실행하지 않고 `failed`로 둔다(로그만). 시간 초과(5.3)도 같다. 다시 실행하기 전에 멈춤, 하루 상한, 사용 한도를 다시 본다.
4. 사용자에게 실패를 알리지 않는다. 예외: 도구가 이미 쓴 `max_turns` 회차는 5.3대로 확인 문구를 보낸다.
5. (b) 전송 뒤 `done`을 기록하기 전에 죽으면 다음 시작 때 같은 본문을 다시 보낼 수 있다(최소 한 번, 틈은 밀리초 단위). 데이터 변경은 되풀이되지 않는다.

### 5.5 할 일과 컨디션

**표** (모든 시각은 UTC ISO 8601 문자열, 날짜는 논리적 날짜 `YYYY-MM-DD`)

`tasks`

| 열 | 형식 | 제약 |
|---|---|---|
| `id` | INTEGER PK | |
| `title` | TEXT | NOT NULL, 1~200자 |
| `status` | TEXT | `draft` / `open` / `done` / `dropped`. `draft`는 비서가 제안하고 사용자가 아직 확정하지 않은 할 일 (5.7) |
| `planned_for` | TEXT 날짜, NULL 가능 | 하려는 날. 마감일이 아니다(P2) |
| `scheduled_at` | TEXT 시각, NULL 가능 | 시각이 정해진 일 (예: 치과 14:00) |
| `parent_id` | INTEGER FK tasks, NULL 가능 | 값이 있으면 첫 걸음이다 (`is_first_step` 열은 두지 않는다) |
| `note` | TEXT | |
| `created_at`, `updated_at` | TEXT | NOT NULL |
| `completed_at` | TEXT, NULL 가능 | `status='done'`일 때만 값 (CHECK) |
| `deleted_at` | TEXT, NULL 가능 | 소프트 삭제. 도구로는 쓰지 않음(관리용) |

`task_areas(task_id, area)`: PK `(task_id, area)`, `area` CHECK 6개 값. 할 일마다 최소 1개(도구가 검증).

`task_events(id, task_id, kind, payload_json, at)`: `kind` ∈ `proposed`, `confirmed`, `created`, `updated`, `completed`, `moved`, `dropped`, `reopened`. SP3 경험치 원장의 근거.

`tool_events_log(id, run_id, conversation_id, task_id, kind, at, inbound_id, data_json)`: 변경 도구가 데이터 변경과 같은 트랜잭션에서 쓴다. 재실행 판정(5.4-3), "전부 추가" 버튼(그 대화에서 제안된 초안 찾기), 사용자 메시지 다시 넣기(5.2, `inbound_id`)에 쓴다. `data_json`은 확인 문구와 초안 버튼을 다시 만들 ToolEvent 데이터(제목 등)다. DB에만 있고 로그 파일에는 쓰지 않는다. `record_condition`은 이 표에 쓰지 않는다(같은 날짜를 덮어써서 다시 실행해도 같다).

`priorities(cadence, period, rank, task_id)`: PK `(cadence, period, rank)`, UNIQUE `(cadence, period, task_id)`, `rank` CHECK 1~3. 할 일이 `dropped`가 되면 해당 우선순위 행을 지운다. `period` 형식: 일 `2026-10-23`, 주 `2026-W43`(ISO 주), 월 `2026-10`, 분기 `2026-Q4`, 년 `2026`. 목표(월·분기·년 우선순위)도 이 표에 들어간다.

`conditions(date, score, note, recorded_at)`: PK `date`, `score` CHECK 1~5. 같은 날 다시 기록하면 점수를 덮어쓴다. 메모 없이 다시 기록하면(버튼) 있던 메모는 지우지 않는다. 오늘(논리적 날짜)보다 뒤의 날짜는 기록하지 않는다.

**도구** (MCP 서버 `planner`)

| 도구 | 입력 | 하는 일 | ToolEvent |
|---|---|---|---|
| `add_task` | title, areas, planned_for?, scheduled_at?, parent_id?, note? | 추가. **사용자가 직접 추가해 달라고 한 할 일에만** 쓴다 | `task_added` |
| `propose_tasks` | 할 일 목록(add_task와 같은 필드) | 비서가 제안하는 할 일을 `draft`로 저장 | `tasks_proposed` |
| `confirm_tasks` | ids | 초안을 `open`으로 확정 | `tasks_confirmed` |
| `update_task` | id, title?, areas?, note?, scheduled_at? | 바꾸기 (날짜는 `move_task`) | `task_updated` |
| `move_task` | id, planned_for (NULL 가능) | 하려는 날만 바꾼다 | `task_moved` |
| `complete_task` | id | 완료 | `task_completed` |
| `reopen_task` | id | 전에 열려 있던 할 일만 `open`으로 되돌린다: `done` → `open`, `dropped` → `open`(내려놓기 전에 `open`이었을 때만). 빠지거나 만료된 초안은 되돌리지 않는다(사용자가 확정한 적이 없다) | `task_reopened` |
| `drop_task` | id | 내려놓기 | `task_dropped` |
| `list_tasks` | status?, from?, to?, area?, limit≤50 | 조회. status가 없으면 `open`만(초안은 `status="draft"`로 물을 때만) | 없음 |
| `set_priorities` | cadence, period, task_ids(≤3, 순서가 순위) | 해당 기간 우선순위를 통째로 교체. 4개 이상이면 거절 | `priorities_set` |
| `record_condition` | date?(기본 오늘), score 1~5, note? | 기록 | 없음 |
| `read_transcript` | from, to (최대 7일) | 원문 기록 읽기 | 없음 |

**날짜와 시각 규칙**: `move_task`는 `scheduled_at`이 있는 할 일의 날짜를 새 날로 옮기고 한국 시간 시각은 그대로 둔다. 시각이 00:00~03:59이면 옮긴 `scheduled_at`의 논리적 날짜가 새 `planned_for`가 되도록 달력 날짜는 하루 뒤로 둔다. 날짜를 NULL로 옮기면 `planned_for`와 `scheduled_at`을 모두 지운다. `scheduled_at`을 바꾸는 `update_task`는 `planned_for`를 새 시각의 논리적 날짜(04:00 경계)로 다시 정한다.

**확인 문구**: 도구 함수가 돌려준 `ToolEvent`를 호출 단위 컨텍스트(`RunContext`)에 쌓는다. 두뇌 호출이 끝나면 하네스가 이벤트를 문구로 바꿔 **두뇌 답변 아래에 한 메시지로 붙여** 보낸다. 예: `✓ 추가: 치과 (10/25 14:00)`, `✓ 옮김: 운동 → 내일`. 두뇌가 답변에서 같은 내용을 말해도 확인 문구는 항상 붙인다. 이벤트별 문구 전체는 부록 A에 있다.

변경 도구 호출 뒤마다 `data/exports/tasks.md`를 다시 만든다.

### 5.6 텔레그램 명령

명령은 두뇌를 거치지 않고 하네스가 도구 함수를 직접 부른다(마스터 5.5).

| 명령 | 동작 |
|---|---|
| `/today` | 오늘 우선순위, 일정, 열린 할 일 |
| `/week` | 이번 주 우선순위와 할 일 |
| `/pause <일수>` | 지금부터 N×24시간 동안 `morning_brief`, `evening_checkin`, `review(week)`를 멈춘다(1~14). 끝 시각을 `app_state.pause_until`에 저장. 멈춘 회차는 `skipped(paused)`. 사용자 메시지에는 계속 답한다. 쉬는 것도 정당하다(P3) |
| `/unpause` | 멈춤 해제 |
| `/plan [주제]` | 계획 모드 시작 (5.7) |
| `/done` | 계획 모드 끝내기 |
| `/help` | 명령 목록 |

`/status`(SP3), `/memory`(SP2)는 해당 하위 프로젝트에서 추가한다. 명령의 답 문구(사용법, 멈춤·해제, 계획 모드, `/help`, 빈 `/today`·`/week`)는 부록 A에 있다. `/pause`의 일수가 정수가 아니거나 1~14 밖이면 사용법으로 답한다.

### 5.7 초안 할 일과 계획 모드

**원칙**: 할 일 목록에는 사용자가 동의한 것만 올라간다(결정은 사용자가 한다).

| 누가 꺼냈나 | 저장 방식 |
|---|---|
| 사용자가 "치과 추가해 줘"처럼 직접 말함 | `add_task`로 바로 `open` |
| 비서가 브리핑, 체크인, 회고, 계획 모드에서 제안함 | `propose_tasks`로 `draft`. 메시지 아래에 초안마다 `✓ 추가` `✗ 빼기` 인라인 버튼을 붙이고, "전부 추가"도 둔다 |

- 버튼은 두뇌를 거치지 않고 하네스가 `confirm_tasks`나 `drop_task`를 직접 부른다. 자연어로 "좋아, 그거 다 넣어"라고 해도 두뇌가 `confirm_tasks`를 부른다.
- **버튼 모양** (티켓 06 결정): 초안마다 한 줄에 `✓ 추가: {제목}`과 `✗ 빼기`를 둔다. 제목은 16자까지 보이고, 넘으면 15자 + `…`이다(여러 줄을 구별할 수 있게). 맨 아래 줄은 `전부 추가`다. 컨디션 버튼(5.4)이 함께 붙으면 초안 줄 다음에 `1`~`5` 한 줄을 둔다. 메시지가 길어 나뉘면 버튼은 마지막 조각에만 붙는다.
- `전부 추가`는 그 대화에서 제안해 아직 초안인 할 일을 모두 확정한다. 같은 호출에서 이미 확정한 초안에는 버튼을 붙이지 않는다.
- 이미 초안이 아닌 할 일의 버튼(지난 메시지의 버튼)을 누르면 아무것도 바꾸지 않고 "이미 정리된 할 일이에요."라고 알린다. 누를 때의 알림 문구는 부록 A에 있다.
- 초안은 우선순위에 올릴 수 없다. `set_priorities`는 `open` 할 일만 받는다.
- 3일 동안 확정하지 않은 초안은 조용히 `dropped`로 바꾼다(알리지 않음). `/today`와 아침 브리핑은 초안을 보여 주지 않는다.

**계획 모드 (`/plan [주제]`)**

사용자와 비서가 할 일이나 목표를 함께 의논하는 대화다. 비서가 일방적으로 목록을 만들지 않는다.

1. `/plan [주제]`로 시작한다. 대화 종류 `plan`을 연다. 사용자가 글로 "같이 계획 세우자"라고 하면 비서가 `/plan`을 안내한다(하네스는 자연어로 모드를 바꾸지 않는다).
2. 비서는 **질문을 한 번에 하나씩** 하며 무엇을, 왜, 언제쯤 할지 좁힌다. 목표가 크면 우선순위와 15~30분짜리 첫 걸음으로 쪼갠다.
3. 의논이 모이면 초안 목록을 `propose_tasks`로 보여 주고 버튼으로 확정받는다. 우선순위 지정도 사용자 확인 후에 한다.
4. `/done`으로 끝나고("여기까지"라고 하면 비서가 `/done`을 안내한다), 마지막 활동 뒤 2시간이 지나면 저절로 닫힌다(30분 규칙을 쓰지 않는다). 만료는 tick마다 확인해 닫는다(5.3). 활동은 사용자 메시지와, 그 계획 대화에서 제안한 초안의 버튼 누름이다(티켓 11 결정). `/plan`을 다시 보내면 열려 있던 계획 대화를 닫고 새로 연다. 주제가 없으면 "계획 모드 시작"을 주제로 넘긴다.
5. 계획 모드 동안 시작되는 회차는 계획 대화가 닫힐 때까지 미룬다. tick은 한계 안의 회차를 판정하지 않고 `pending`으로 두고, 한계를 넘은 회차는 `skipped(late)`로 둔다. 이미 큐에 든 회차가 꺼낼 때 계획 대화가 열려 있으면 건너뛰지 않고 `pending`으로 되돌린다(넘겨 받은 회고는 표시를 먼저 되돌린다). 다음 tick이 다시 판정한다. 계획 모드 중 5분 뒤 재전송은 그대로 보낸다(두뇌는 이미 끝났다).

반복 할 일(매일 운동 등)은 SP1에서 만들지 않는다. 필요해지면 계획 모드에서 사용자와 의논해 별도 설계로 추가한다.

### 5.8 원문 기록

- 하네스가 쓴다. 두뇌에게는 읽기 도구만 있다.
- 파일: `data/transcripts/YYYY/MM/YYYY-MM-DD.md` (논리적 날짜 기준)
- 형식: 메시지마다 `### HH:MM 사용자|비서 [대화 ID] (회차 키)` 머리글과 본문. 대화 밖의 명령, 버튼, 고정 안내는 `[-]`로 쓴다(예: `[버튼] 컨디션 4`). 도구 호출은 `> 도구: add_task` 한 줄(인자 없이)로 남긴다.
- 덧붙이기만 한다. 수정하지 않는다.
- 본문 줄이 `### `로 시작하면 앞에 U+200B(폭 없는 공백)를 붙여 쓴다. 사용자가 붙여 넣은 머리글 모양 줄이 새 메시지로 읽히지 않게 한다.
- **가리기**: 사용자 메시지를 원문 기록에 쓰기 **전에**, `inbound_pending`에 저장하기 **전에**, 그리고 두뇌에 넘기기 **전에** `redact.py`를 적용한다. 가린 자리는 `[가림]`으로 바꾼다. 가린 일이 있으면 두뇌 컨텍스트에 "인증·식별 정보를 가렸음"을 알린다. 대상과 예외(스펙 갭 6, 최종 리뷰 Minor 4 결정):
  - 주민등록번호(외국인등록번호 포함) 형식: 6자리-7자리, 뒷자리 첫 숫자 1~8.
  - 계좌번호로 보이는 숫자열: 숫자와 하이픈으로 이어진 덩어리 중 숫자가 10~14자리인 것.
  - "비밀번호/비번/패스워드/핀번호/password/passwd/PIN" 뒤의 값. 값에는 영문자나 숫자(ASCII)가 하나 이상 있어야 한다. 그래서 "비밀번호 변경했어?", "비번 바꿨어?"는 가리지 않는다. 기호나 전각 글자만으로 된 값도 가리지 않는다.
  - **가리지 않는 전화번호**(계좌번호 판정보다 먼저 뺀다): 휴대전화 `01X-XXX(X)-XXXX`(하이픈 없어도 됨), 유선 `02-XXX(X)-XXXX`, `0XX-XXX(X)-XXXX`(지역번호 `0[3-6][1-5]` 꼴, 031~064), 인터넷 전화 `070-XXX(X)-XXXX`(유선과 070은 하이픈이 있어야 한다. 하이픈 없는 10~11자리는 계좌번호와 구별할 수 없어 가린다), `+82` 국제 형식(앞의 0을 뺀 휴대전화·유선 번호, 구분은 하이픈·공백·없음).
  - **카드번호(15~16자리)는 가리지 않는다.** 10~14자리 규칙 밖이다. SP1 범위 밖으로 두고 사용자 안내 문서에 "민감한 정보는 보내지 않는 편이 안전하다"고 적는다.

## 6. 시스템 프롬프트 원칙

`harness/prompts/system.md`에 담는다. 문구는 구현 단계에서 다듬되 이 원칙은 바꾸지 않는다.

1. 한국어 존댓말, 짧게. 한 메시지는 휴대폰 한 화면 안.
2. 우선순위는 최대 3개, 첫 걸음은 15~30분 크기로 제안한다.
3. 마감, 나이, 남은 시간으로 압박하지 않는다. 금지어 "밀렸다", "놓쳤다", "실패", "놓쳤어요", "밀렸어요", "늦었지만"을 쓰지 않는다(정본과 확인 방법은 5.4 "문구 규칙").
4. 컨디션이 2 이하면 할 일을 줄이자고 먼저 제안한다.
5. 휴식은 할 일과 같은 무게로 다룬다.
6. 결정은 사용자가 한다. 비서는 초안과 선택지를 낸다.
7. 데이터 변경은 반드시 도구로 한다. 도구 없이 "저장했어요"라고 말하지 않는다.
8. `[가림]`으로 바뀐 정보는 저장되지 않았다고 짧게 알린다.

**통합 테스트**: 가짜 봇 + `FakeBrain`(도구 호출 시나리오 재생) + 임시 SQLite로 다음을 확인한다.
- 메시지 처리 전체 흐름
- 회차와 사용자 메시지가 겹칠 때 직렬 처리 순서
- 전송 실패 후 재시도에서 도구가 다시 실행되지 않음
- 크래시 후 `running` 회차 복구

**반자동 점검**: 작업 스케줄러 XML 스키마 검증, 등록 후 `schtasks /query /xml` 결과 비교.

**수동 수용 테스트**: 1장의 완료 조건 1~5를 노트북에서 7일 동안 확인하고 체크리스트로 남긴다. 실제 Claude를 부르는 것은 스파이크와 수동 수용 테스트뿐이다.

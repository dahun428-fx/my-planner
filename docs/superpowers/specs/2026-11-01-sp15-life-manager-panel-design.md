# SP15 라이프 매니저와 전문가 패널 상세 설계 (추가 기능)

- 상태: 승인 (2026-11-01, v1.1)
- v1.2 정정 (2026-11-01, 구현 계획에서 정한 것): 패널 제안 표에 `per_week`·`conversation_id` 칸을 둔다. 남은 수 문구는 "이번 주 제안 n개 더 받을 수 있어요"("남음"은 금지어). 전체 진단은 오류·시간 초과에 다시 시도하지 않고 고정 답으로 끝나며, 리포트를 저장한 뒤 실패하면 저장됐다는 고정 답을 준다. 받은 할 일을 버리면 제안은 `dismissed`, 습관은 그 주 횟수를 채우면 `done`, 예측 창(기한+14일)이 값 없이 닫히면 `checked_at`만 채운다. 축 예측은 그 축 점수가 읽는 지표로만 맞춰 본다. 이미지 전문가는 사진 바이트 없이 글만 받고, 내장 서브에이전트(`general-purpose` 등)는 훅이 거절한다. 패널 API는 대시보드에 403이고, `/panel/budget` 응답에 `full_diagnosis_ok`가 있으며, 새 경로 `GET /owner-statements`와 `/actions retire_statement`를 둔다. 전체 진단 횟수는 리포트를 저장한 진단만 센다. 보통 매니저 메시지 한도는 `limits.manager_message`. 받은편지함 사건의 ref는 행이 지워져도 근거·관찰 참조로 받는다.

## 1. 목표와 완료 조건

2026-11-01 점검에서 리포트 v1은 "점수표"였고, v2는 전문가 6명의 처방이었지만 이번 주 할 일이 18개라 "이상적인 사람"의 처방이었다. Dahun은 전문가들과 앱 안에서 **계속 주고받으며** 리포트를 키워 가기를, 그리고 처방이 **'나'라는 사람 안의 근거**로 현실적이기를 원한다. 앱이 내 성향과 현실을 반영하며 진화해 온 것처럼 이것도 점차 진화해야 한다(2026-11-01).

**완료 조건 (수용 기준)**

1. 앱 채팅 시트의 상대 고르기에 "라이프 매니저"가 있다. 라이프 매니저 대화는 비서·운동메이트 대화와 목록이 따로다.
2. "연봉이 오르면 결혼 시장 점수는 어떻게 돼?"라고 물으면, 라이프 매니저가 커리어·관계 전문가를 불러 소견을 받고 한 목소리로 답한다. 답 아래 "전문가 소견 2개" 접힌 줄이 있고 펴면 각 원문이 보인다.
3. 라이프 매니저의 할 일·습관 제안은 언제나 **패널 제안 카드**다. 카드에는 "근거 보기"가 있고, 펴면 근거가 "내 기록 / 내가 한 말 / 외부 기준"으로 나뉘어 보이며 각 줄을 누르면 그 기록(할 일, 메모, 내가 한 말, 측정값)으로 간다.
4. 내 기록이나 내가 한 말 근거가 하나도 없는 제안은 서버가 버린다. 외부 기준만 있는 내용은 카드가 아니라 답 안의 "참고" 문단으로만 보인다.
5. 한 주(월~일)에 새로 나오는 패널 제안 카드는 "주간 제안 수"를 넘지 않는다. 처음 4주는 2개이고, 이후 매주 월요일에 지난 4주 패널 제안의 결과로 1~5 사이에서 다시 정한다(7장).
6. 패널 제안을 받으면 할 일·습관이 된다. 버릴 때는 이유 칩(시간 없음 / 관심 없음 / 이미 하는 중 / 너무 큼 / 그냥)을 고를 수 있다. 그 결과가 다음 제안의 크기와 시기를 바꾸고, 같은 영역에서 같은 이유가 두 번이면 "내가 한 말"(`preference`)로 남는다.
7. 근거가 부족한 영역(예: 관계)에서는 라이프 매니저가 제안 대신 질문을 한다("지난달 사적으로 만난 사람이 몇 명이었어요?"). 답은 "내가 한 말"(5.4)이나 측정값(확인 카드)이 되고 다음 근거가 된다.
8. 목표 숫자는 내 기록에서 출발한다: 지난 8주 헬스 평균 주 2회면 다음 목표는 주 2~3회이지 주 4회가 아니다(8장 내 속도 표).
9. 라이프 매니저가 "90일 뒤 체지방 15%"처럼 예측을 말하면 예측 표에 남고, 기한이 지나면 실제 측정값과 맞춰 보고 다음 목표를 보정한다(9장).
10. 충돌 정리 순서: ① Dahun이 내린 결정 ② 건강·돈 위험 ③ 이번 주 여력 ④ 효과 크기. "커리어 먼저, 연애 병행" 결정 아래에서 심리 전문가가 "관계 먼저"를 말해도 답은 커리어를 주축으로 한다.
11. "전체 진단" 칩을 누르면 전문가 6명이 모두 돌고, 인생 리포트(앱 화면 `/status/report/`)가 새로 만들어진다. 리포트 v2와 같은 장(세 통로 요약, 점수판, 지렛대 지도, 전문가 소견, 3년 하면/안 하면, 90일 로드맵, 이번 주)을 갖되 "이번 주"는 주간 제안 수 안의 카드만이다.
12. 건강 전문가는 진단과 목표만 정하고, 운동 루틴은 운동메이트에게 넘긴다. 넘기는 건 라이프 매니저가 하루 끝 판단에서 SP14 `hand_off`로 한다(전문가는 도구가 없다).
13. 라이프 매니저와 전문가는 먼저 말하지 않는다. 하루 끝 판단의 관찰 한 줄만 마스터의 아침 브리핑을 거친다(SP14).
14. 14장의 자동 테스트가 모두 통과한다.

## 5. 라이프 매니저 (대화 상대)

### 5.1 `024_life_manager.sql`

- `conversations.agent`, `inbound_pending.agent`의 CHECK에 `manager`를 더한다(SP12 ADR 0019가 예고한 마이그레이션). SQLite는 CHECK를 바꿀 수 없으므로 표를 새로 만들어 옮긴다(SP 마이그레이션 훅 방식, `hooks.py`).
- 대화 고르기는 SP12 5.2와 같다(30분 규칙만, 회차·계획 없음).
- 같은 마이그레이션에 `owner_statements`(5.4), `panel_suggestions`(7.1), `panel_predictions`(9.1), `life_reports`(10장)를 만든다.

### 5.2 지시문 `manager.md`

- 역할: 판단을 돕는 조율자. 답은 짧고, 이번 주 하나에 집중한다.
- 충돌 정리 순서(1장 10). Dahun의 결정 목록은 `decisions` 블록으로 앞머리에 들어간다(`owner_statements` 가운데 `decision` 종류. 이 스펙 3장 결정은 마이그레이션이 처음 줄로 넣는다).
- 전문가 부르기: 한 메시지에 많아야 2명. "전체 진단"일 때만 6명.
- 근거 규칙(Q5), 질문 먼저(근거 부족), 외부 기준만이면 "참고".
- 금지: 비율(%), 연속 기록, "못 했다", "뒤처졌다", 다른 사람과의 등수 비교. 점수와 자기가치 분리 문장(심리 전문가 "이 숫자는 이번 분기 조건의 측정값이지 나 자신이 아니다")을 전체 진단 끝에 늘 붙인다.

### 5.4 내가 한 말 (`owner_statements`)

SP2 기억층(기억 카드, `search_memory`)은 아직 코드에 없다. 그래서 근거의 "내가 한 말"을 담을 작은 표를 이 스펙이 만든다. SP2를 만들 때 기억 카드가 이 표를 흡수한다(그때 `statement:<id>` 참조를 옮기는 마이그레이션).

```sql
CREATE TABLE owner_statements (
  id         INTEGER PRIMARY KEY,
  kind       TEXT NOT NULL CHECK (kind IN ('fact','preference','decision')),
  area       TEXT CHECK (area IN ('career','finance','health','relationships','learning','quality_of_life')),
  key        TEXT UNIQUE,                 -- decision만: 'career_first' 같은 짧은 키
  text       TEXT NOT NULL CHECK (length(text) <= 200),
  source_ref TEXT,                        -- 'conversation:<id>' 또는 'suggestion:<id>'
  created_at TEXT NOT NULL,
  retired_at TEXT                         -- 내가 "그건 이제 아니야"라고 하면 채움(지우지 않음)
);
```

- 쓰는 길: 라이프 매니저 도구 `save_statement {kind, area, text}`(질문에 대한 내 답, 대화 중 "나는 ~하고 싶어"), 그리고 7.4의 버리기 이유 규칙(코드). 확인 카드 없이 조용히 저장한다(마스터 설계의 기억 카드 규칙과 같다: 비밀번호·주민번호 같은 식별 정보는 금지어 검사로 막는다).
- 보기·고치기: 더보기 > "내가 한 말" 목록에서 지우기(`retired_at`)만. 지운 줄은 근거로 쓰지 못한다.
- 왜 기억 카드를 기다리지 않나: SP2는 임베딩·검색까지 큰 일이고, 근거 검사에는 id로 찾을 수 있는 줄만 있으면 된다.

| `health` 건강 전문의 | `experts/health.md` | 측정값(건강·외모), 몸 기록, 운동 기록, 컨디션 |

| `relationship` 관계 코치 | `experts/relationship.md` | 일정(제목 없이 시각·종류만), 측정값(관계), 내가 한 말, 할 일(관계) |
| `psych` 심리 코치 | `experts/psych.md` | 컨디션, 이룬 순간, 인생 곡선(민감 사건 가림 그대로), 분기 회고, 패널 제안 결과 |

- 전문가 지시문은 프로젝트 폴더 `social-level/experts/` 소견서의 관점과 "하지 말 것"을 옮긴다. 개인 숫자는 넣지 않는다(앞머리에서 온다).
- 모든 전문가는 쓰기 도구가 없다. 결과는 라이프 매니저에게 돌려주는 글뿐이다.
- 외부 기준은 SP13 기준표만 읽는다(`read_benchmark {key}`). 웹 검색 도구는 없다(13장).

### 6.2 호출 상한

- 라이프 매니저 대화의 메시지 하나 = 두뇌 호출 하나(서브에이전트 포함). 서브에이전트 호출은 그 안에서 많아야 2개, "전체 진단"은 6개.
- 전체 진단은 하루 1회, 주 2회 상한. 넘으면 칩이 "오늘은 이미 했어요"로 바뀐다.
- 모두 `daily_brain_calls`에 센다(SDK 호출 하나 = 1). 서브에이전트 6개가 도는 전체 진단은 실제 사용량이 1보다 크다. 그래서 전체 진단은 따로 `limits.full_diagnosis`(`max_turns` 30, `brain_timeout_s` 900)를 쓰고, 사용자 몫(`MOMENTS_RESERVE_CALLS`)이 3 이상 남아야 시작한다. 이 값이 맞는지는 스파이크 S1에서 잰다(실제 토큰 사용과 시간).

## 7. 패널 제안

### 7.1 `panel_suggestions` (마이그레이션 024에 함께)

```sql
CREATE TABLE panel_suggestions (
  id           INTEGER PRIMARY KEY,
  conversation_id INTEGER REFERENCES conversations(id),
  kind         TEXT NOT NULL CHECK (kind IN ('task','habit')),
  title        TEXT NOT NULL,
  area         TEXT NOT NULL CHECK (area IN ('career','finance','health','relationships','learning','quality_of_life')),
  size_min     INTEGER NOT NULL CHECK (size_min BETWEEN 5 AND 120),  -- 예상 소요(분)
  due_hint     TEXT,                                 -- 'YYYY-MM-DD' 또는 NULL
  experts      TEXT NOT NULL,                        -- 'career,finance'
  evidence_json TEXT NOT NULL,                       -- 7.2
  week         TEXT NOT NULL,                        -- 'YYYY-Www' 나온 주
  state        TEXT NOT NULL CHECK (state IN ('proposed','accepted','done','postponed','dismissed','expired')),
  result_ref   TEXT,                                 -- 받으면 'task:<id>' / 'habit:<id>'
  dismiss_reason TEXT CHECK (dismiss_reason IN ('no_time','not_interested','already','too_big','none')),
  created_at   TEXT NOT NULL,
  decided_at   TEXT
);
```

- 왜 할 일 표에 `draft` 상태를 두지 않고 새 표인가: 근거·전문가·버리기 이유·주 같은 칸은 할 일에 없고, 버린 제안도 남아야 주간 제안 수를 계산할 수 있다. 할 일 표는 받은 뒤에만 생긴다.
- 상태 흐름: `proposed` → 받기 `accepted`(할 일·습관 생성) → 그 할 일이 완료되면 `done`, 날짜가 뒤로 미뤄지면 `postponed`(다시 완료되면 `done`) / 버리기 `dismissed` / 7일 동안 아무것도 안 하면 `expired`.
- `accepted` 뒤 상태는 SP14 사건(`task_done`, `task_postponed`)을 보고 하루 끝 판단이 갱신한다(두뇌 없이 코드).
- 받기·버리기는 SP14 사건 `suggestion_accepted`·`suggestion_dismissed`(`ref` = `suggestion:<id>`)를 같은 트랜잭션에 남긴다.
- 받아서 생긴 할 일에는 일반 할 일 경험치(X1)만 붙는다. 패널 제안에 따로 경험치를 주지 않는다(같은 일을 두 번 세지 않게).

### 7.2 근거 검사 (코드, `panel/evidence.py`)

`evidence_json` = `[{type, ref, note}]`.

| `type` | `ref` 모양 | 검사 |
|---|---|---|
| `record` | `task:<id>`, `event:<id>`, `habit:<id>`, `checkin:<date>`, `body_day:<date>`, `workout:<id>`, `measure:<id>`, `moment:<id>`, `suggestion:<id>` | 그 줄이 있고 지워지지 않았다 |
| `statement` | `statement:<id>`, `memo:<id>`, `review:<period>:<area>`, `decision:<key>` | 그 줄이 있다. `statement`·`decision`은 `retired_at`이 비어 있다 |
| `external` | `bench:<표 키>` | SP13 기준표에 그 키가 있다 |

- `record` 또는 `statement`가 하나도 없으면 도구가 `rejected: no_personal_evidence`를 돌려주고 카드가 생기지 않는다. 존재하지 않는 id가 하나라도 있으면 `rejected: unknown_ref`.
- 거절은 두뇌에게 이유와 함께 돌아가고, 두뇌는 질문으로 바꾸거나 근거를 고쳐 다시 낸다(한 메시지에 다시 내기 1회).
- 카드의 "근거 보기"는 `note`(한 줄 설명)와 링크를 보인다. `note`는 120자 이하.

### 7.3 주간 제안 수 (Q4 C, `panel/budget.py` 순수 함수)

```
처음 4주(첫 패널 제안 주부터): 2
그 뒤 매주 월요일, 지난 4주 패널 제안(받거나 버리거나 만료된 것) n개로:
  닫힌 받은 것 = done + postponed               (아직 accepted인 것은 세지 않는다)
  완료율 = done / 닫힌 받은 것                   (닫힌 받은 것이 0이면 완료율 규칙은 건너뛴다)
  거절률 = (dismissed + expired) / n
  다음 수 = 지난 수
           + 1  (완료율 ≥ 0.7 이고 거절률 < 0.3)
           − 1  (완료율 < 0.4 또는 거절률 ≥ 0.5)
           (+1과 −1이 동시에 맞을 수는 없다. 완료율이 없으면 거절률 ≥ 0.5일 때만 −1)
  1 ≤ 다음 수 ≤ 5
n < 3이면 그대로
```

- 완료율·거절률과 주간 상한 숫자는 사용자에게 보이지 않는다(비율 금지). 앱에는 "이번 주 제안 {남은 수}개 남음"만.
- 질문은 제안 수에 세지 않는다.

### 7.4 버리기 이유 → 다음 제안

| 이유 | 다음 제안에 |
|---|---|
| `too_big` | 같은 영역 다음 제안은 `size_min`이 버린 것의 절반 이하여야 한다(코드가 넘으면 `rejected: too_big_again`) |
| `no_time` | 내 속도 표의 빈 시간대(일정 없는 저녁·주말)에만 `due_hint` |
| `already` | 그 내용은 측정값·내가 한 말로 확인 질문 |
| `not_interested` | 같은 영역·같은 전문가 조합의 제목이 비슷한 것(정규화한 제목이 같음)을 30일 안 다시 내면 코드가 `rejected: not_interested_recent` |

같은 영역에서 같은 이유가 2회면 코드가 "내가 한 말"(`preference` 종류, 예: "커리어 제안이 너무 크다고 두 번 버림")을 만든다. 두뇌를 부르지 않는다.

## 8. 내 속도 표 (`panel/pace.py`, 순수 함수)

앞머리에 들어가는 표. 모두 내 기록에서 계산한다.

| 항목 | 계산 |
|---|---|
| 한 주에 끝낸 할 일 | 지난 8주 평균, 영역별 |
| 미룬 할 일 | 지난 4주, 영역별 개수와 가장 많이 미룬 요일 |
| 운동한 날 | 지난 8주 주 평균(운동 기록 + 운동 습관) |
| 빈 저녁·주말 | 다음 2주 일정에서 19시 이후 일정 없는 평일 수, 일정 없는 주말 반나절 수 |
| 컨디션 | 지난 4주 평균, 3 이하 날 수 |
| 잠·걸음 | 지난 4주 평균(몸 기록) |
| 패널 제안 결과 | 지난 4주 받음·끝냄·미룸·버림 개수 |

- 목표 규칙(지시문): 새 목표는 내 속도 표 값의 많아야 1.25배에서 출발한다(예: 주 2회 → 2~2.5회). 1.25배를 넘는 목표는 근거로 Dahun의 결정이나 "더 하고 싶다"는 말이 있어야 한다.

## 10. 인생 리포트

- "전체 진단" 칩 → 6명 소견(6.2의 따로 된 한도) → 라이프 매니저가 리포트 JSON을 도구 `save_life_report`로 저장(`life_reports(id, created_at, json)`, 마이그레이션 024).
- JSON 장: `summary`(한 줄 진단과 세 통로), `scores`(SP13 값 그대로 참조), `levers`(행동 → 축 연결, 강약), `experts`(6개: 한 줄 진단, 처방 3~4줄, 하지 말 것), `scenario`(3년 하면/안 하면, 추정 표시), `roadmap`(90일 트랙과 KPI), `this_week`(그 주의 패널 제안 id들), `questions`(남은 질문).
- 앱 화면 `/status/report/`: 리포트 v2 HTML의 장 구성과 시각화(레이더, 지렛대 지도, 덤벨, 간트)를 앱 컴포넌트로. 상태창 "객관적 위치 자세히" 옆에 "인생 리포트" 줄.
- 분기 회고가 끝나면 비서가 "전체 진단 해 볼까요?"를 제안 칩으로 붙인다(자동 실행은 하지 않음).
- 지난 리포트는 목록으로 남는다(비교용). 점수 숫자는 저장 시점 값의 사본이다.

## 13. 외부 기준과 개인정보

- 전문가는 웹을 검색하지 않는다. 외부 숫자는 SP13 기준표에서만 온다. 그래서 "시장 상황" 같은 최신 정보는 기준표 갱신(해마다) 수준으로만 반영된다. 이건 의도한 한계다(근거를 따라갈 수 있게).
- 두뇌로 가는 앞머리에는 측정값 숫자(연봉, 자산, 체성분)가 들어간다. 이 글은 채팅과 같은 경로로 Anthropic에 가고 SDK 세션 파일과 원문 기록 md에 남는다(ADR 0019와 같은 대가). 대화 원문 기록은 비서의 `read_transcript`가 읽지 않는다.
- 로그에는 숫자를 남기지 않는다.
